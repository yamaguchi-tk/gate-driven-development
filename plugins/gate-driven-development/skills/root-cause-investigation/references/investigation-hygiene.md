# Investigation Hygiene（認知バイアス対策・6 原則）詳細

`root-cause-investigation` skill の Investigation Hygiene セクションの詳細版。禁則・チェックテンプレ・過去の違反実例をまとめる。4 Phases の中で繰り返し陥る認知バイアスを防ぐための横断ガードレール。Phase 1〜4 のどこでも常時適用する。

**重要**: これは **model 性能では防げない種類のミス**で、上位モデル（Opus 等）でも同じ罠にかかる。skill 側の強制力で初めて回避できる。事実、後述「失敗実例」では Opus でこの 6 原則がいずれも踏まれずに誤った root cause を確定し、ナレッジとして文書化してしまった。

## 原則 1: Scope Expansion Before Narrowing（早期スコープ固定の防止）

ユーザーが指した対象だけでなく、**同じコンテキスト（時間帯・環境・親リソース・同 deploy・同 session）で同時に動いていた他のエンティティを最初に列挙**してから絞る。

| 適用ドメイン | 「他のエンティティ」の例 |
|---|---|
| AWS / インフラ | 同クラスタの全サービス、同 VPC の全 SG、同 role を持つ全リソース、同時刻の全 API 呼び出し |
| アプリ / バグ調査 | 同時刻の他リクエスト、同 user session の前後操作、同 deploy で変更された全ファイル |
| パフォーマンス | 同 host の他プロセス、同 DB の他クエリ |
| テスト失敗 | 同 fixture を使う他テスト、同 mock を持つ他 case |

**禁則**: ユーザーが質問した対象だけで証跡フィルタを掛ける（`ResourceName` 指定 / 特定 test だけ実行 / 報告サービスのログだけ見る等）を**初手にしない**。スコープを意図的に広げてから観測する。

**チェック**: 「同じ時間帯に走っていた他のエンティティを 1 つ以上挙げよ」「同じ親リソース配下に他に何があるか挙げよ」を Phase 1 で必ず実施。

## 原則 2: Configuration / Rule の意味的評価

設定や rule を**取得しただけで結論材料に使わず**、「この設定は実際に何にマッチ / 何を許可 / 何を拒否するか」を 1 文で言語化してから推論に進む。

| 適用域 | 評価すべきこと |
|---|---|
| EventBridge / SNS filter / IAM / SG | prefix / suffix / wildcard / 階層構造（ARN 等）が実際の input にどうマッチするか |
| 正規表現 | 実際にマッチするサンプル / マッチしないサンプル |
| feature flag / cron / route | 実際に有効になる user / 時刻 / path の条件 |

**禁則**: 設定 JSON を取得しただけで「ルール側は正しそう」と判断しない。

**チェック**: 「この filter は実際の input X1, X2, X3 のうちどれにマッチするか？マッチしないか？」を観測 input で評価。

## 原則 3: Multiple Working Hypotheses（対立仮説 3+ 生成）

未知の観測（不明 ID、想定外の値、説明できない症状）には**最低 3 つの競合仮説**を並べ、各仮説を棄却するまで結論しない。

**禁則**: 「これは X だろう」で 1 仮説に飛ばない。「ephemeral」「内部生成」「観測ミス」等の lazy attribution は単独で結論にしない。

**チェックテンプレ**:
```
観測 X に対する対立仮説:
- A: <最有力候補>
- B: <隣接ドメイン / 別エンティティ由来>
- C: <時間軸の別断面 / 過去残骸>
- D: <観測ミス / ツールの仕様>
検証コマンド: 各仮説 1 コマンドで棄却可能か明示
```

## 原則 4: 非対称性は仮説棄却の Primary Signal

**「同一条件で異なる結果」が観測されたとき、`仕様起因 / プロトコル起因` 仮説は原則不成立**。差分を先に潰す。

適用例: 2 つの similar service で挙動が違う → 仕様ではなく環境差・隣接リソース・依存差を先に疑う / 2 user / 2 region / 2 env で違う → 環境固有の状態を先に疑う / 2 test で挙動が違う → fixture / mock / order 依存を先に疑う

**禁則**: 非対称性を「規模差」「設定値の微差」「キャッシュ差」等の補強仮説で**塗りつぶさない**。それは強化バイアス。

**チェック**: 「この仮説 H が仕様起因なら、A と B の両方で同じ結果になるはず → なっていない → H は要再考」を明示する。

## 原則 5: 一次出典の直接読み取り（Source Bias 対策）

検索結果のサマリーや AI 要約だけで結論を出さない。**判定格上げ（suspected → confirmed）の前に一次出典を直接取得して context 込みで引用**する。

| 適用域 | 一次出典 |
|---|---|
| 仕様・公式挙動 | 公式 docs を WebFetch（検索スニペットは NG） |
| ライブラリ挙動 | 該当バージョンの source code / changelog |
| API 仕様 | OpenAPI schema / 実 response の生 JSON |
| 過去ナレッジ | 本文を直接取得（リンク先のタイトルだけで判断しない） |

**禁則**: WebSearch の 1 文で `suspected → 確定` に格上げしない。「公式 docs にこう書いてあった」を本文確認なしに引用しない。

**チェック**: 仕様 / 公式挙動の引用は、必ず原典 URL と引用文の context（前後 1 段落）を証拠に添える。

## 原則 6: 反証ステップの明示（Confirmation Bias 対策）

仮説形成後、必ず**「この仮説が誤りなら何が観測されるはず？」**を書き出し、その観測を能動的に探す。

**禁則**: 仮説形成後に「裏付け（X が観測されたか）」だけを集め、「反証（Y が観測されたら仮説棄却）」を集めない。

**テンプレ**:
```
仮説 H: <仮説>
H が正しいなら観測されるはず: X1, X2, X3
H が誤りなら観測されるはず: Y1, Y2, Y3
確認した観測:
- X1: ✅ / ❌ / 未確認
- Y1: ✅ / ❌ / 未確認  ← Y が観測されたら仮説棄却
```

## 失敗実例（Why this matters）

これら 6 原則がいずれも踏まれずに発生した実例（ある通知ノイズの調査）:

- **原則 1 違反**: CloudTrail で同クラスタ別サービスの UpdateService を観測したが、「別サービスだから無関係」と即断 → 真因（別サービスの event 混入）を最後まで見落とし / **原則 2 違反**: EventBridge rule の `resources` filter を取得したが、prefix match と ARN 階層の組み合わせを評価せず → cluster 全体フィルタになっていたことを見落とし / **原則 3 違反**: 不明 deployment ID を「ephemeral 内部 ID」と単一仮説で結論 → 「別サービスの deployment ID」という対立仮説を立てず
- **原則 4 違反**: 2 サービスの非対称性（サービス A=1 件 / サービス B=2 件）を「DesiredCount 差で統合された」と補強仮説で塗りつぶし → 仕様起因仮説を棄却すべき signal を取りこぼし
- **原則 5 違反**: WebSearch スニペットの「multiple state change events」を AWS 公式仕様として `suspected → 確定` に格上げ → 後の検証で原典に該当文言が無いと判明 / **原則 6 違反**: 仮説形成後、裏付け証拠だけを収集 → 「別サービスの UpdateService」という反証可能 signal は既に scope 外として視界から消えていた

**結論**: これらは Opus でも防げなかった。model 性能を上げても認知バイアスは減らない。**skill 側で強制力を持って 6 原則を回す以外に再発防止策は無い**。
