# Independent Review

> **所有**: 独立レビュー（実装文脈から切り離した 1 回のレビュー）の契約
> **参照元**: `references/self-review-lanes.md`（発火表・`dry` 判定）、`skills/gdd-pr-review/SKILL.md`（Pre-Push Self Review）、`skills/gdd-pr-review-followup/SKILL.md`（merge gate 証跡）、`skills/pr-review-followup/SKILL.md`（GDD 非依存の独立レビュー契約参照。`state.md` への証跡記録は要求しない）
> **Why**: 2026-09-06 に reviewer の検出力を調べると、自己周回（3 レーン）は確定した欠陥を 1 件も拾えず `approved` を出した。周回数ではなく「実装文脈を持たない読み手」が検出力を持つ

## 契約（4 条件すべてを満たすときだけ独立レビューと呼ぶ）

1. **実装文脈を渡さない**: headless / subagent として起動し、requirements・design・reviews・worklog・本セッションの会話を渡さない。渡すのは diff とリポジトリの read-only アクセスだけ
2. **read-only**: 使用ツールは Read / Grep / Glob 相当に限る。artifact もコードも変更しない
3. **diff-only**: レビュー対象は push 対象 tip の diff。証跡の `context` は `diff-only` 固定。**2 回目以降の起動範囲（同一 PR 内での再起動）**は次の (3-a)〜(3-e) と (3-f) の取り直しに従う（(3-f) の severity と category の基準は 1 回目から当てる）。規定を足すときは、1 文に継ぎ足さずいずれかの項へ入れる（1 文へ詰め続けた結果、主節と後置の限定句が食い違う退行が起きた）。
   - **(3-a) 絞り込みの可否**: 本条でいう**対象**は、差分とその影響先（変更したシンボルの呼び出し元・同じ入力を読む別の実装）を指す。分岐ごとに書き分けない。**main session が** `state.md` の既存 `Independent Review` 行を読み、その `<sha>` と `high` / `blocking` を前回証跡として使う（読んだ後にレビュー結果で上書きする）。行が無ければ 1 回目とみなし、push 対象 tip の全差分（本条の既定）を対象にする。行があり、かつ前回証跡の `high` と `blocking` が両方 0 の場合（2 回目以降）だけ（と (3-f) の取り直しの `decision-only`）、前回証跡の `<sha>` から今回の push 対象 tip までの差分を対象にする。証跡行は `sha | reviewer | context | high | medium | blocking | at` の件数のみで finding の識別子を持たないため、差分だけでは前回 finding が解消したかを検証できない。証跡行の `<sha>` は絞り込みの有無にかかわらず、従来どおり **push 対象 ref の tip** に合わせる（§ 証跡 の引き継ぎを除く。§ 証跡・pre-push gate・pre-PR gate の sha 一致検査は変えない）。次のいずれかに当たる場合は絞り込みを行わず、**全量**（push 対象 tip の全差分）を対象にする（fail-closed）
     - 前回証跡の `high` または `blocking` が 0 でなかった
     - 前回証跡の行が `references/self-review-lanes.md` § merge gate 証跡 の書式として valid でない（必須 key の欠落、`high` / `blocking` が uint として読めない場合を含む）か、`blocking` key を欠く旧書式行（`legacy-no-blocking-field`）である——前者は前回証跡の値が読めないので、前回の独立レビューを前提にできない（`standard` では、前回の push で pre-push gate がその不足を通知している。止めはしない）。後者は gate を通るが `blocking` の件数が不明なため、絞り込みの前提（前回が両方 0）を満たせない
     - 前回証跡の `<sha>` が現在の履歴から解決できない、または push 対象 tip の祖先でない（force-push / rebase 等で履歴が書き換わった場合を含む）——書き換え後も旧 commit は解決できてしまうため、解決可能性ではなく祖先関係で判定する
     - 前回証跡の `<sha>` が今回の push 対象 tip と同じ（差分が空）
   - **(3-b) 範囲の判定**: (3-c) の計上義務に当たらない finding について、範囲外（(3-a) が対象とした差分にも、その影響先にも当たらない箇所）への新規指摘は `advisory` とする。新しい情報の根拠（前回レビューでは見えなかった実装の実態・新たに判明した依存関係等）を示せる場合は**範囲内**として扱う。範囲内として扱った finding は `medium` に数える（証跡に `low` カウンタは無いため、medium 以下はすべて `medium` に数える。`high` / `blocking` の計上先は (3-c) が正本。`blocking` は `is_blocking(category)` が単独正本なので、本項が直接動かすことはない）。範囲内か範囲外かを判定できない finding は**範囲内**として扱う（fail-closed）
   - **(3-c) 計上義務**: **範囲外でも severity High または実害クラス（正本: `references/reviewer-common.md` § finding category）の finding は `advisory` にせず、新しい情報の根拠が無くても計上する。High は `high` に、実害クラスは `blocking` に計上する（両方に当たるなら両方。`blocking` は `is_blocking(category)` に従う）**。`high` に計上した finding は `medium` に二重計上しない。前回までに出てまだ解消していない `high`・`blocking` は、範囲外のままでも計上を続ける（独立レビュアーは前回の finding 一覧を持たないため、独立レビューが再報告しなかった分は main session が件数に足す）。計上した `high`・`blocking` は当該 push で 0 まで解消する。別 PR へ切り出せるのは (3-d) の降格が許される finding だけである
     - 受理述語は `high: 0` かつ `blocking: 0` であり、独立レビューを要求する `standard` の pre-push / pre-PR gate は、計上したまま push・PR 作成をしたら実行後に通知し、would-block を記録する（止めはしない。`trivial` / `quick (express)` / `quick (standard)` は独立レビュー自体を要求しない（pre-push gate が複数の steering から push 対象 tip の証跡で 1 件を選んだときは、Task Size によらず要求する）。merge gate が本行を読むのは `Bot Review Received: received: no` かつ `Last Review Push At` が valid な経路のみである。`Last Review Push At` が無効なら merge gate 側の別 reason code を通知するが、`received: yes` の経路では本行を読まず reason code も積まない（`Pre-Merge Review Recheck` と `Merge Approval` の不足を通知する。merge gate は止めない））
   - **(3-d) 降格規定の非適用**: **範囲内か範囲外かを問わず、severity High または実害クラスの finding には**、severity を引き下げる規定（`references/self-contained-contract.md` § plugin が内包すべき必須契約 の reviewer calibration 契約 Stage 2、impl gate 手順 5 の 1 段階降格）と、finding を `advisory` へ落とす規定（`requirements.md` § Honest Limitations 既載の例外、`references/reviewer-common.md` § Finding の由来と scope の `origin: pre-existing` の既定、impl gate 1c の Reviewer File Scope Constraint）を、名称を問わず**適用しない**。適用できるのは、**severity が medium 以下で、かつ実害クラスでない** finding に限る（`references/self-review-lanes.md` の `dry` 判定に calibration を適用しないのと同じ封鎖。§ 常時 High と実害クラスは別概念で、実害クラスには常時 High に含まれない category があるため、severity だけで許可集合を書くと medium × 実害クラスが `blocking` の計上から漏れる）
   - **(3-e) followup との分担**: PR 後の周回でも独立レビューの起動範囲の基準点は本条の前回証跡 `<sha>` のままで、`skills/gdd-pr-review-followup/SKILL.md` § 差分スコープ の `last_head` は PR レビュー finding の対応範囲と `範囲外 blocker` の強制発火にのみ用いる（計上義務の正本は本条）
   - **(3-f) 後で実装する guard・contract test の Decision**: finding の `file:line` が、後続で実装する guard・contract test の要件を定める文（ADR・guardrail の Decision）に当たるときは、文字どおりに読むと文自体が違反を許す（fail-open の向き）ときだけ high にし、`references/reviewer-common.md` § 常時 High と実害クラスはそのまま当てる。列挙の外の経路 P で抜けられる型で、文字どおりの読みでは P も違反になる（後続の test が落ちる側に倒れる）なら、§ 常時 High の 4 型に数えず medium 以下にし、category は同ファイル § finding category のテストの判別力不足の値にして（実害クラスを付けない）、修正案を後続の test の要件として書く。承認済みの Decision の列挙の形への finding も、high でなければ同じ category にする（実害クラスを付けない）。この型の severity と category は本項が正本で、§ 常時 High と § finding category より先に当たる。この型と、承認済みの Decision の列挙の形への finding のうち、medium 以下で実害クラスでないものは、`skills/gdd-implementation-gating/SKILL.md` でも `skills/gdd-completion-check/SKILL.md` でも advisory として記録し、下の申し送りに回す。high・実害クラスは通常どおり差し戻す。design gate では `references/requirements-gating-steps.md` の blocking の述語に当たるときだけ直す。文が後続の guard・contract test の要件を定めるか、どちらに倒れるかを判定できなければ、本項を当てない（§ 常時 High と通常の基準のまま）。この基準は reviewer が出力するときに当てる常設の方針で（契約 1 の渡すものを広げない）、(3-d) の降格に当たらない。main session は reviewer が付けた severity・category を (3-f) で変えず、(3-c) のとおり数える。Why: GDD を使う別の repo の PR（2026-10-12〜13）では、実装仕様を列挙した Decision の外の経路が独立レビューのたびに high になり、確定した文面を何度も開き直した。守る事実と「判定できない形は失敗」に書き直すと high が 0 になった
     - **直し方と取り直し**: high は実装仕様の列挙を足さず、守る事実（主体ごとに誰が何をできるか）と「判定できない形は失敗」に書き直して直す（列挙を足す修正は `references/reviewer-common.md` § Fix の影響範囲 の `閉じ方: 列挙`）。書き直した後の独立レビュー（取り直し）は 1 PR あたり 1 回で、gate の Round 上限・`Pre-PR Fix Attempts` とは別に数える。取り直しを始めるとき main session は `state.md` § Gate Status に `- Decision Retake: used | prior_sha: <前回証跡の sha> | prior_findings: <decision-only | mixed> | at: <ISO 8601>` を 1 行書く（前回の high・blocking がすべて Decision への finding のときだけ `decision-only`、それ以外は `mixed`）。行があれば取り直しは使用済みとする。`decision-only` なら、(3-a) の 1 つ目の条件に当たっても、対象を前回証跡の `<sha>` からの差分にする（(3-a) のほかの条件に当たれば全差分。(3-c) の計上は変えない）。`mixed`、行を読めない、前回の finding が Decision への指摘か確かめられないときは全差分にする。取り直しでも high または blocking が残れば、書き直しを重ねず人に戻す。PR 作成前は `references/post-completion-pr-flow.md` の昇格処理の順序 3（`Pre-PR Fix Attempts` の値によらない）、PR 作成後は `skills/gdd-pr-review-followup/SKILL.md` の方式転換を `human_recheck_required` で人に戻す。後続の test の要件として書かれた修正案は、main session が Issue に写し（後続で test を書く task があれば、その要件にも写す）、申し送りの正本をその Issue とする。写したら `state.md` § Gate Status に `- Decision Handoff: issue: #<N>[, #<M>] | at: <ISO 8601>` を 1 行書く（申し送りが無ければ行を書かず、`none` とも書かない。この語が state.md にあれば、pre-PR gate は Task Size・理由によらず `ADR distilled: not_applicable` を実行後に通知する。値の書式は検査しない）。あわせて、申し送った Decision は Task Size によらず repo ADR へ蒸留し（`references/adr-vs-design.md` § Distill 対象）、その Consequences に「この Decision の guard・contract test を実装するときは Issue #<N> の要件を満たす」と書く（蒸留の前に申し送ったときは steering の `adr.md` の Consequences に書き、蒸留で repo ADR へ運ぶ）。guard・contract test を実装する作業はその Decision を読むので、そこから Issue に届く。`Medium Disposition` を書くときは `recorded` にその Issue 参照を書く
4. **モデル**: `references/fixed-models.md` の **`independent_review` tier**（モデル・effort・host 別写像の正本はそちら。本節では再掲しない）。Claude Code では `subagent_type: gate-driven-development:gdd-independent-reviewer`（`agents/gdd-independent-reviewer.md`。model と effort は定義で固定）で起動し、`model` を渡さない。コストが高いため発火は **push 1 回あたり 1 回**に絞る

## 観点レーン（順に適用し、レーンごとに最低 1 回は実コードを読んでから結論する）

- **(a) 接地**: diff が前提にする既存機構（出力の配信経路・既存 hook・外部依存）が実在し、想定どおり届くかを実装で確認する
- **(b) 内部整合**: 同じ概念が複数の節・複数ファイルで定義されている箇所を列挙し、片方だけ更新された痕跡を疑って突合する
- **(c) 測定設計**: 各 AC の測定単位と記録 schema の粒度が一致するか。記録が完了判定まで生存するか
- **(d) 実装接続**: 変更する既存コードの分岐順序・単位・既存 counter / TTL / escape hatch との相互作用を、該当関数を実際に読んで追跡する
- **(e) 記録監査**: 「反映済み」「処置済み」「閉包が成立」等の断定を、実装のリテラル・集合と逐条突合する
- **(f) 実効性**: 各 AC が目的を実際に達成するか。既存の escape hatch や既定値により上限・強制が bound として機能しない経路がないか
- **(g) 例外で guard 全体が落ちる経路**: 新規コードが既存 deny より前に実行される場合、例外（encode / parse / resolve / stat / 型違い）が捕捉されずに非 block 終了し、既存 deny が 1 件も走らない経路がないか。lone surrogate・NUL・非 dict payload・相対パスを 1 形ずつ当てる
- **(h) 受理集合の対称性・列挙型判定の検出**: 同じ入力を読む関数が複数あるとき（parser と判定、top-level と nested）、受理するキー・別名・型の集合が一致するか。片方だけが受理する入力で「片方は判定・片方は素通り」にならないか。また、判定が「既知の異常パターンを列挙して弾く」型になっていないか。列挙型なら受理文法のホワイトリスト化・既定の反転への置き換えを見る（個別ケースを塞ぐパッチは別の変異で再発しやすい。review-log-present.sh の fence-parsing・identity marker 判定で同じ型の穴が何度も再発したことから 2026-09-16 に追加）

(g) (h) は 2026-09-06 に追加した。(a)〜(f) だけの構成では、例外による fail-open（(g) 相当）を実際に見逃していた。checklist 側の対応項目は `references/inline-review-checklists.md` § 推論型。

## 出力フォーマット

finding ごとに severity（high / medium / low）/ category（正本: `references/reviewer-common.md` § finding category）/ `origin: this-diff | pre-existing`（正本: 同 § Finding の由来と scope）/ `file:line` / 修正案 を必ず添える。severity の判定は `reviewer-common.md` に従い、§ 常時 High（deny 迂回・guard bypass・fail-open・例外で guard が落ちる） の適用範囲に当たる finding は下げない（適用範囲外の扱いと、`blocking` を数える named alias「実害クラス」との関係は同節が正本。`blocking` は § finding category の `is_blocking` で数える）。後続で実装する guard・contract test の要件を定める Decision への finding は、契約 3 の (3-f) の基準で severity と category を決める。0 件なら「なし」と明記する。finding には 1 から始まる通し番号を付け、最後の行に `findings: <finding の数>`（0 件でも）を書く（main が `review-findings.md` に写す。正本: `references/finding-dispositions.md`）。PR 後の followup では main session が別 field `fix_origin: self-inflicted | inherited` を finding に付ける（reviewer は付けない。算出規則の正本は `skills/gdd-pr-review-followup/SKILL.md` Step 3 (b)。`origin` とは値域を混ぜない）。

## 証跡

`state.md` の `## Gate Status` 節に `Independent Review` 行として記録する。書式は merge gate と同一（正本: `references/self-review-lanes.md` § merge gate 証跡）。行を書く前に、その巡の全 finding の行き先を `review-findings.md` の `IR` 節に書く（(3-c) で main が足す未解消の high・blocking も行にする。行き先の値域と、行の件数の数え方の正本は `references/finding-dispositions.md`。push・PR の前の `check-gate-ledger.sh` の `findings` 行が、この行の sha・件数と突き合わせる）。

```
- Independent Review: <sha> | reviewer: <agent-name> | context: diff-only | high: <uint> | medium: <uint> | blocking: <uint> | at: <ISO 8601>
```

push 前は `<sha>` を **push 対象 ref の tip** に合わせる（pre-push gate が一致を検査する）。PR 作成前と merge 前は HEAD に合わせる（pre-PR gate が一致を検査する。merge gate が検査するのは、契約 3 の (3-c) のとおり `Bot Review Received: received: no` の経路だけ）。default branch を取り込むだけの merge commit では、`references/self-review-lanes.md` § Independent Review の引き継ぎのとおり、旧 sha の行のまま引き継げる。`high: 0` かつ `blocking: 0` でなければ、pre-push gate・pre-PR gate が実行後に通知し、would-block を記録する（止めはしない。受理述語の正本。merge gate も同じ述語）。範囲外で見つかった finding も、契約 3 により `advisory` にできないものは `high` / `blocking` の件数に数える。
