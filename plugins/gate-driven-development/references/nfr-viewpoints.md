# Non-Functional Requirements Viewpoints (性能・拡張性 / 移行性 / セキュリティ / システム環境)

> **所有**: 非機能要求グレードの残り4視点（性能・拡張性/移行性/セキュリティ/システム環境）の観点breakdown
> **参照元**: `gdd-requirements-gating`（Non-Functional Requirements Check）

## Purpose

`Non-Functional Requirements Check` の可用性（耐障害性/回復性）・運用保守性（障害時運用）は、べき等性・リトライ発火という具体例まで `skills/gdd-requirements-gating/SKILL.md` にinline anchoringされている。残り4視点は要件ごとの該当有無が大きく揺れるため、視点名だけを渡すのではなく、ここに**観点breakdown**を置く。

IPA非機能要求グレードの6視点という骨格は借りるが、中項目をそのまま網羅転記はしない。本プラグインが扱うタスク領域（ソフトウェア/インフラ/エージェントワークフロー）で実際に効く観点だけに絞っている。各項目は**Yes/No判定基準ではなく、検討を促す問い**として書く。数値閾値・合否条件はここで固定せず、要件ごとにAIまたは人間が判断する。

## 観点集

### 性能・拡張性

該当要件例: 高負荷・急激なトラフィック増加・データ量増加が想定される要件

- 想定を超えるリクエスト増加時の挙動（レート制限/キューイング/バックプレッシャー）は検討されているか
- データ量増加に伴う処理時間・クエリ性能の劣化は考慮されているか
- 将来のスケールアウト/スケールイン方針（水平方向の拡張余地）は考慮されているか

### 移行性

該当要件例: 既存データ・既存システムからの移行を伴う要件

- 移行手順と、移行失敗時の切り戻し（ロールバック）手順は明記されているか
- 移行中に新旧が並行稼働する場合、データ・状態の整合性は保たれるか
- 移行失敗をどう検知するか（サイレント失敗にならないか）

### セキュリティ

該当要件例: 認証・認可・機密情報を扱う要件

`skills/gdd-requirements-gating/SKILL.md` の `Fail-closed Default / Untrusted Input Boundary Check` が同じ領域をより具体的にカバーするため、重複指摘を避ける。ここでは同 Check の対象外になりやすい観点だけを補う。

- 認可境界（誰がどの操作を実行できるか）は要件から一意に決まるか
- 機密情報（credential / secret / PII）の保存先・受け渡し経路は明記されているか

### システム環境

該当要件例: 新規外部依存の追加・実行環境の変更を伴う要件

- 実行環境の制約（OS/ランタイムバージョン、CI環境、社内ネットワーク境界）は明記されているか
- 新規外部依存サービスの可用性・レート制限は考慮されているか
- dev/staging/prod 等の環境差分（設定値・認証情報の分離）は考慮されているか

## Medium finding にする条件（reviewer向け）

`skills/gdd-requirements-gating/SKILL.md` のトリガー文に該当する要件特性がある場合のみ、対応する観点の欠落を Medium finding として報告する。該当要件特性がない場合は、この観点集を理由に finding を作らない（false positive 防止）。
