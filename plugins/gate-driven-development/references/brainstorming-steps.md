# Brainstorming Steps（詳細手順）

> `skills/gdd-brainstorming/SKILL.md` の Step Execution から参照される詳細手順の正本。
> Step 番号・§ 名は他 skill / references / tests から参照される契約。変更時は参照元と契約テストを同時に更新する。

過去セッション事例の一次記録・詳細な背景説明は `docs/references-archive/brainstorming-steps-pre-r9-2-original.md` を参照（本ファイルは意図と契約に圧縮したもの。判断に迷ったら原本を読む）。

## Steps

1. **self-contained contract の確認**: `references/self-contained-contract.md` を読み、entry intent・active steering の決定規則・fail-closed 条件を確認する。`references/state-machine.md` は intent が ambiguous の場合か fail-closed の根拠が必要な場合のみ読む。

2. **entry intent の判定**: `references/entry-intent.md` に従い `new` / `resume` / `amendment` / `ambiguous` を判定する。`amendment` は `gdd-requirements-amendment` に委譲する。`ambiguous` の場合は `参照した正本` / `停止理由` / `次の1アクション` を返し、`<gdd-stop reason="blocked">` とその後の `## 👤 次にすること` で fail-closed 停止する（推測で進めない）。

   2a. **Step-by-Step Clarification Loop**: requirements を固めると誤決定になりやすいかを先に確認する。
   - **発火条件**（いずれか）: 依頼が複数領域にまたがる / 根本原因が未特定のまま解決策が指定されている / 技術選定が要件を左右する / 背景・制約が不明で skill が推測で決めることになる
   - **発火しない条件**: 単一領域で scope が明確 / resume / ユーザーが既に判断材料を全て提示している
   - 進め方: 1〜2 軸ずつ複数ターンで確認する。質問は A/B/C の選択式に単純化し、推奨デフォルトを出せる場合は添える（推奨だけで確定しない。採用すると何を捨てるかを 1 行添える）
   - ready criteria（目的 / scope / 成功条件 / 優先度 / 責務境界)を満たしたら、回答済みの内容を `$ARGUMENTS` 相当の確定情報として扱い、`Intake Brief`（目的 / 確定事項 / 未確定事項 / 前提）に整理して artifact に追記する。作成後に質問停止しない
   - ready が未充足なら `Intake Pause` として停止理由を出力して停止する

3. **resume 判定**: `.steering/<task>/state.md` があれば `Resume From` に従って途中から再開する。無ければ new として続行する。

4. **worktree の解決**: `skills/gdd-using-git-worktrees/SKILL.md` に従い worktree を確定する。**Root Branch Creation 禁止**: root repo 上で `git switch -c` / `git checkout -b` / `git branch <name>` によるブランチ作成を行わない。worktree setup is mandatory — 必ず `git worktree add -b <branch-name> <full-path> <default-branch>` で default branch 起点の worktree を作る。An existing `codex/YYYYMMDD-*` branch does not satisfy the GDD worktree contract。A worktree created from `HEAD` is not enough — local `main` / `master` / `develop` を fetch で最新化してから起点にする。既存 root 作業がある場合の migration は worktree 側へ移してから続行する。作成後は `scripts/assert-worktree-ready.py` を pre-artifact で実行し、root に `.steering/` を作る前に失敗させる。作成に失敗した場合は、失敗理由と復旧手順を返して停止する。root との状態分離を保つため `$WORKTREE_ABS_PATH` を明示的に確定させ、以降の Step は全てその配下で行う。

5. **steering path の決定**: `.steering/<task-slug>/` を **必ず絶対パスで指定**して作成する（`$WORKTREE_ABS_PATH/.steering/<task-slug>/`）。`state.md` を作る書き込みで、`Started At` と一緒に `Created In Session: <Bash の printenv CLAUDE_CODE_SESSION_ID の値>` を書く（request-capture-hook が、steering を作った session かを照合する）。値が取れないとき（Codex・Cursor など）は行を書かない。再開では書かず、書き換えない。

6. **運用レベルの宣言**: `references/operation-levels.md` に従い operation level と作業場所を宣言する。

7. **task size の判定**: `references/task-sizing.md`（正本）で quick / standard / express を暫定判定する。artifact-less trivial（`.steering/` を作成しない）の判定も同ファイルに従う。

   7s. **Complexity Evaluation（早見）**: § 12a の 5 次元で暫定スコアを付け、size 判定の補助にする（正本は task-sizing § 正式判定）。

   7t. **技術的不確実性の申告**: 未知の外部依存・未検証の技術前提がある場合はここで申告し、Step 10 の spike 対象にする。

   7b. **Direct Intent 判定**（§ Direct Intent 判定 — `references/task-sizing.md` から正本指定）: ユーザーが実装方式まで具体的に指定しているかをスコアリングし、該当時は Step 9（Problem Discovery の深掘り）・10（Options Exploration）・16（Iterative Refinement）を縮退する。
   - スコア: 変更対象ファイル・関数を名指し **+2** / 実装方式・ライブラリを指定 **+1** / 期待入出力を具体提示 **+1** / 過去に同型タスクの実績あり **+1** / 目的だけで手段未指定 **-3**
   - 合計 **3 以上**で Direct Intent 該当。`references/task-sizing.md` § quick (express) の条件（4 条件）を既に通過している場合はこの判定を省略してよい。
   - 記録: `requirements.md` に `<!-- Direct Intent: score=N, signals=[...] -->` を残す（後続 gate が参照する）
   - 縮退内容: Step 9 は § 現状の把握と § 変更対象パスの存在確認と § 依頼と既存コードの突き合わせのみ実施 / Step 10 は skip（Scope Reduction の縮小案は Human Check Questions へ直接追加）/ Step 16 は 1 周のみ
   - Direct Intent は「最初の要件の輪郭」に対する暫定判断。要件が変われば § 要件変更時の再評価 trigger で無効化する

8. **最新技術情報の確認**: ユーザーの入力に具体的な技術名（framework / library / cloud service / AI service 等）が明示されている場合のみ、version-sensitive / fast-moving かを判断し、最新の公式ドキュメント / release notes / migration guide を確認する（`tech-docs-searcher` 優先、無ければ host の web/doc search）。実装アプローチが技術的に非自明な場合は `similar-case-researcher` 等で類似事例を調査し `findings.md` に記録する。技術名が無ければスキップし、不明点は `Open Questions` に記録する。内部コードの変更のみなら省略してよい。

   8a. **外部 API 統合チェック（External API Integration Check）**: 外部 API 連携が要件に含まれる場合、レスポンスのサンプル JSON（必要フィールドが直接含まれるか、別エンドポイントでの間接解決が必要か）/ 認証方式（PAT, OAuth, API Key）と取得元（SecretsManager 等）/ レートリミット・ページネーション仕様を確認し、`Summary Brief` の `外部依存の確認結果`（express の雛形では `外部依存`）に記録し、未解決の点は `Open Questions` に書く（例: ある外部 API は組織の表示名を含まず別エンドポイントの事前取得が必要だった）。
   - **外部形式の実測（External Format Sampling）**: AC か design が、この repo の外で作られるデータ（API 応答・通知 payload・Webhook・ログ書式など）の欄の位置か値の形を前提にするなら該当する。producer のコード・文書・組み立て直した sample を読むだけでは足りない。該当したら、`requirements.md` の AC を書く前（requirements-gating より前）に、次の実測を済ませる。①読み取り専用の操作（get / list / describe / 履歴の読み出し）だけで実データを取る。書き込み・通知の再送はしない。secret・認証情報・token を返す操作（`get-secret-value`・`--with-decryption` など）は使わず、secret の名前・置き場所は値を返さない操作（`describe-secret` など）で得る。値のキー構造が要るときは、マスク済みの sample をユーザーに求める。取る範囲（期間・件数。producer や通知の種類ごとに 1 件以上）を決め、`findings.md` に書く ②生データは worktree の外（scratchpad など）に置く ③構造（欄の位置・入れ子）と値の形（`<URL|表示名>` のような包み方・桁・区切り）と件数を保ち、値を合成値に置き換えた fixture を worktree の中に作る。テストで使う fixture は、テストの fixture 置き場に置く（`.steering/` は PR に入らず、steering write guard は 12 桁の数字などを deny して値の形を崩させる）。作ったら生データを消す ④実値（ID・URL・本文・個人情報・secret）を、ログ・`findings.md`・steering・commit に書かない。`findings.md` には取得元・範囲・件数・値の形ごとの件数・欄の位置・fixture のパスだけを書く ⑤AC は fixture を根拠に書く。取れないときは、AC に「未測」と理由（権限が無い、まだ発生していない など）を書き、取得手段を `Human Check Questions` に出す。推測した形で AC を確定しない（2026-10-02 の例: 組み立て直した fixture から欄を `attachments[].text` と推測し、レビューを何度も重ねた後に取った生 JSON では `attachments[].blocks[].fields` だった）
   8b. **Runtime 環境変数の依存（Runtime Environment Variable Dependencies）**: 新機能が Runtime 環境変数を必要とする場合、環境変数名・用途・値の取得元 / IaC（Terraform `agent_runtime_env` 等）への反映先 / 必要な IAM 権限（`secretsmanager:GetSecretValue` 等）を `requirements.md` に明記する（要件段階で網羅できていれば実装フェーズの手戻りが減る）。
   8c. **Migration / Conversion タスク判定（Format Conversion Check）**: 既存ファイルを別フォーマットへ変換する種類のタスク（`.md` → `.yml`、JSON → YAML、framework A → B、table markup → form field 等）を検知した場合、**AC-F1（原文保全）/ AC-F2（変換先ネイティブ機能の活用）/ AC-F3（content-diff 検証）/ AC-F4（レンダリング確認）** を `受入条件` に必須で含める（構造変換の AC だけを書き、原文保全の AC が無かったために、PR の後のレビューで内容の欠落が見つかって手戻りした事例）。
   8d. **IDE 互換の確認**: `~/.claude/skills/`・`~/.claude/plugins/`・`hooks/scripts/`・`settings.json`・`SKILL.md`・`CLAUDE.md` を変更するタスクでは、Claude Code CLI と IDE（Cursor 等）の両方で動くかを要件に明記する（「IDE でも動くようにして」という後追い修正が 20260419 / 20260423 / 20260427 / 20260501 で反復発生）。
   8e. **Command Interface の事前確定**: コマンド・CLI の引数体系やインターフェース設計が human check に未確定のまま出ると、修正版の再提示が反復する（実際に何度も繰り返した）。設計インターフェースは brainstorming 中に確定させ、要件に明記する。
   8f. **実行・評価環境の現実確認**: command / agent / model / provider の想定が実行環境・評価ハーネスで実際に成立するか（実行経路、モデル指定の反映、評価データの取得可否）を設計前に確認し、findings.md に記録する。
   8g. **Technology Stack Fit Check（技術スタック適合確認）**: 外部サービス、SDK、CLI、MCP、API、framework、runtime、IaC provider、DB、AI model/eval 基盤を新規採用または変更する場合、requirements.md を書く前に採用方式の候補を比較する。
   - 適用トリガー: 外部サービスや vendor integration を使う / `MCP / CLI / SDK / API` のように複数の access method が自然に存在する / credential backend（Secrets Manager / SSM / env / OAuth 等）・multi-tenant・account/service/env 切替が設計に影響する / repo に既存の同種パターンがあり新規採用方式がそれと違う
   - 調査内容: **公式統合**（vendor official MCP / SDK / managed integration / CLI / API があるか、GA / preview / deprecated / unavailable のどれか）/ 既存標準（repo の既存 dependency・runtime helper・Terraform module・project skill・運用手順に合うか）/ access method 候補比較 / credential・tenant 境界（secret 実値をどこにも出さない境界）/ testability（unit / contract / E2E / external evidence のどこで検証できるか）
   - 記録先: 調査ログと根拠は `findings.md`。requirements.md に書くのは承認判断に効く結論だけ（採用方式と理由は `実装方針` へ、後戻りが高い採用技術・access method・credential backend は `Human Check Questions` の承認ポイントへ）
   - 判断ルール: 公式統合があればまず第一候補にする（別方式を採るなら理由を明記）。候補が 1 つしかないように見えても `Existing repo standard` と `Official integration` は必ず確認する。multi-tenant / credential backend / access method が未確定なら、AI が仮決定したまま silent に実装へ進まず HITL に出す（Datadog 連携で direct API helper を先に設計し「公式 MCP が GA」「複数テナントで account 切替が必要」と後から判明して技術スタックがズレた事例）
   8h. **検証手段の妥当性確認**: 検証を実行する前に、その検証セットアップで目的の改善が実際に計測できるかを確認する（どの検証タイプにも適用する汎用チェック）: false pass の防止（壊れた実装が検証を通過しない設計か）/ 改善前後で観測値が動く構造か（不変量を計測していないか）/ 検証環境・ハーネス・ツールの制約（eval ハーネスの MCP 無効化等）を確認済みか / 検証結果がどう解釈されるかを設計前に明示する（OK 条件 / NG 条件）。懸念が残る場合は `findings.md` に記録し、AC の書き方（観測可能な claim）へ反映する。

9. **Problem Discovery（問題の具体化）**: requirements.md を書き始める前に、以下を実施する。曖昧な理解のまま書くと human check で「そもそもなぜ？」に戻る。
   - **Current State Verification Check（現状確認）**: 対象コードパスが既存 PR・既存実装で対応済みでないかを `git log` / `gh pr list` / `grep` で確認する（既存 PR で対応済みの前提を確かめずに要件を組み立て、実装の直前で `planning_rework_required` になった事例の再発防止）。タスクが触れうる**全実行経路**（MCP ラッパー / Bash / subagent / SDK 等）を列挙してから調査範囲を確定する（MCP ラッパーの経路だけを調べ、Bash・subagent 経由の経路を最初から対象外にしていた事例の再発防止）
   - **過去の判断の参照**: `docs/learned-patterns.md` があれば読む（`references/cross-task-learning.md` 参照）
   - **ユーザー提供の参考情報の確認**: ユーザーが渡した URL・記事・既存コードパスは requirements を書く前に読み、内容を findings.md に残す。参考情報を無視して独自に方針を決めない
   - **現状の把握**: 変更対象のコード・設定・画面を読み、変更が関係するシナリオが現在どう処理されるかを**動作の視点**で確認する。呼び出し元・エントリポイントから変更対象まで辿り、既存の条件分岐・前処理・ガードを把握してから要件化する（対象ファイル単体読みは周辺処理と衝突する設計を生む）
   - **Existing Code Reading Evidence（既存コード読解証跡）**: 既存コード・workflow・skill/plugin/hook の変更では、既存コードのどこを読んだか（責務・正本・consumer・runtime 設定）を `findings.md` に記録する。target file only is shallow — 変更対象ファイルだけでは evidence 不足。責務・正本・consumer・runtime 設定・既存機能・類似実装が曖昧なまま AI が仮決定して HITL へ進まず、gap と検索範囲を記録して段階確認する
   - **Existing Capability / Reuse Check（既存機能・再利用確認）**: 既存機能の変更に見える要件は、ユーザー語彙とコード語彙の両方で検索する。既存機能が見つかったら新設案を既成事実にせず、再利用/新設の判断を `実装方針`（policy-level なら承認ポイント）に出す。見つからない場合も検索語・探索範囲・未発見理由を残す
   - **依頼と既存コードの突き合わせ（Request–Code Crosscheck）**: quick（express を含む）と standard（§ 7b の Direct Intent で 9 を縮めたときも含む）で、requirements.md を書く前に 1 回行う。express から昇格したタスクは着手のときに済んでいるので、昇格のときは、着手の後に `request.md` に入力が足されたときだけ回し直す。trivial では行わない。(1) `.steering/<task>/request.md` に、この作業のきっかけになったユーザーの発言を言い換えずに写す。AskUserQuestion の回答は質問と選んだラベルを写し、発言が assistant の案を番号などで指すときは、指された案の文を assistant の文と分かる形で引用して添える。main の注記（範囲・解釈など）は書かない。ただし Claude Code（`printenv CLAUDE_CODE_SESSION_ID` が値を返すとき）では、runner は `request.md` を作らず、この写しを `.steering/<task>/request-notes.md` に書く。`request.md` は、(2) の起動のときに hook（`hooks/scripts/run-request-capture-hook.sh`）が、main の transcript から写したユーザーの発言の節（`<!-- gdd-request-capture:begin -->` から `end` まで）で新しく作る。この節と、その下に時刻つきで足すユーザーの発言が依頼の原文の正本である。どの形の `request.md` でも、`見直し` で始まる assistant の引用は依頼の原文に数えない。hook は、`/gdd-dev` の起動の後から突き合わせまでのユーザーの発言も、transcript から節の下に時刻つきで写す。写す範囲の終わりは、この steering を作った `/gdd-dev` の起動（`state.md` の `Started At` 以前で最後の起動）である。hook が写すのは、`state.md` の `Created In Session` が今の session の id と一致するときだけである。写せないとき（transcript が無い、欄が無い・違う、その起動か起動より前の発言が transcript に無い、`Started At` が読めない）は、hook は写していないことと理由の見出しの `request.md`（先頭が `<!-- gdd-request-capture:not-copied -->`）を作り、起動の後の発言があれば下に時刻つきで写し、systemMessage でも知らせる。この形の request.md は、初めの依頼の原文が無い状態で、突き合わせ agent はリスクの段を `高` にし、human check は依頼をユーザーに確かめる。steering の書き込み検査は、request.md が hook の節で始まる通常のファイルでないとき（この形、runner・main が書いた、無い）、リスクの段の記録によらず `risk-low` の承認を止める（`hooks/scripts/lib/risk_tier.py`。human check で本人の承認を待つ）。hook は、既にある `request.md` を書き換えない。(2) の後に `request.md` が無ければ（hook が落ちた、kill switch、開き直していない session など）、runner が同じ先頭の行と `## hook は依頼の原文を写していない（hook が書かなかった）` の見出しだけで作り、(3) では突き合わせの出力の代わりに `突き合わせ: unavailable（hook が request.md を作らなかった）` と `### リスクの段`     - 各候補の実装例・既知のハマりポイントを調べる。実際に動いている事例の有無は実現可能性の判断材料（調査手段は環境で利用可能なもの）
    - 技術的不確実性（7t）が残る案は、採用前に最小 spike で検証するか、`unresolved` として Human Check Questions に出す
    - **§ Visual Companion**: UI・画面・出力フォーマットの変更時は、軽量な視覚化を各 Approach の説明直下に `<details>` または inline code fence で添付する（ASCII 図 / Markdown table / **Before/After block**（最推奨。差分が一目で分かる）/ 本格 UI 変更時は `mockup.html` を `/tmp/` に作って `open` する手順だけ提示し承認後の確認をオプション提案する — 自動で起動しない）。比較表が長くなる場合は `mockup.md` を `.steering/<task>/` に作って参照する。mockup の採用案は human check の「承認ポイント」に明示追加する（例: `Approach A の Before/After サンプルの after で進めて良いか`）。skip 条件: 内部 API / 内部ロジック / リファクタ / 設定値変更だけで、ユーザー / レビュアーが目視する出力が変わらない場合は不要

11. `requirements.md` のセクション定義は `references/requirements-template.md` に従う（`quick` パスでは Summary Brief + 目的 + スコープ + AC + 実装方針の最小構成でよい）。確認できない期待は `Non-Goal`、確認できない制約なら `Status: unresolved` として明示し、Yes/No で答えられる形の Human Check Questions に落とす。

    - **罠7（実測義務）**: requirements.md の AC に登場する対象ファイル数・行番号・シンボル・分岐は、requirements-gating に提出する前に実コードを実測して確定する。仮の値・推測値（未確認パスや概算のみの記述）を AC に含めない。実測できない場合は「未測」+ その理由を明示する。

    11a. **完了条件の AC への写し（HITL ズレ防止）**: requirements 初稿を書くとき、trace 表は作らず AC 本体で担保する。
    - ユーザーが最初に言った完了条件・既存実装状態・仮置き・手動設定済み状態は、まず `スコープ` に原文に近い箇条書きで残し（照合元）、そのまま AC に写す（勝手に丸めない・落とさない）。落とす場合は `非スコープ` か `Open Questions` に理由付きで書く
    - AC は Yes/No で観測できる文へ寄せる。claim にできない条件は AI がテストを書いて解釈を固定せず、`Open Questions` か承認ポイントに出す
    - 作り方がズレると後戻りが大きい論点（repo 分割、既存仕組み再利用 vs 新設、import vs recreate、public vs private、CI/CD 方針）は `実装方針` に記録し、policy-level なら承認ポイントに出す（ファイル単位の計画は書き込みすぎず design-gating に送る）

12. lightweight `design.md` skeleton のセクション定義も `references/requirements-template.md` に従う（粒度は同 § lightweight design.md skeleton セクション一覧のとおり。design-gating を通るタスクでは詳細設計の粒度で書く）。planning 中に重要な意思決定や却下した代替案が固まった場合は、任意で active worktree 側 `.steering/.../adr.md` を作成または更新し、`Context` / `Decision` / `Why` / `Consequences` を追記してよい。
    - **design.md skeleton は HOW（実装方針）と WHERE（変更予定ファイルの実パス・行番号）を、後続の human check Decision Packet にそのまま出せる粒度まで this step で書く。詳細を design-gating に先送りする形で WHERE を空欄・仮パスのまま残さない。**

    12a. **Complexity Evaluation（複雑さ評価）**: requirements.md の初稿が書けたら、`references/task-sizing.md` § 正式判定: Complexity Evaluation に従って 5 次元（Scope Breadth / AC Complexity / Integration Depth / Safety Surface / Uncertainty）を低/中/高で評価し、推奨 sizing を算出する。
    - Step 7 の暫定 sizing と比較する: **一致** → そのまま進む / **推奨が重い方向** → 昇格を提案し理由を表示。ユーザーが承認すれば昇格して artifact 構成を追加する / **推奨が軽い方向** → 降格は提案しない（既に重い方の構成で作業しているため）
    - 評価結果は `requirements.md` の `Task Size` 行の直後にコメントで記録する: `<!-- Complexity: Scope低 / AC中 / Integration低 / Safety低 / Uncertainty低 -->`
    - Step 7 で `quick (express)` と判定した場合はこの Step をスキップする（express は `references/task-sizing.md` § 判定基準 の 4 条件で決める）。ユーザーが明示指定した sizing は Complexity Evaluation より優先する

### § 要件変更時の再評価 trigger

human-check の往復で要件が追加・拡張されたとき、初期 sizing をそのまま維持しない。修正反映後に以下のいずれかが該当した場合、再提示の前に Complexity Evaluation を再実行する:

- **(a) AC 数が +2 以上 または +50% 以上 増加した**（同一の事象を複数フォーマット・方法で検出する variant は sub-condition として 1 AC にまとめる。別の事象を対象にする条件は独立 AC）
- **(b) 独立した検出パターン・条件カテゴリ・分岐ルールが +1 以上 増加した**（同一カテゴリ内の値追加は除く）
- **(c) 新規の外部依存・他コンポーネント影響・Python/IaC 両方の変更が判明した**
- **(d) AI が「却下した代替案」を 2 件以上書く必要が生じた**（≒ 設計判断が選択肢相当）

特に重要なのは `quick (express) → quick (standard)` の昇格判断。Express は Options Exploration と Iterative Refinement Loop を skip するため、要件が複雑化したまま Express で進めるとエッジケース探索が抜け落ち、レビュー段階での手戻りが発生する。express で範囲か Files が変わったら、再提示の前に requirements-gating をもう 1 Round 回し、reviewer が express の条件を確かめる（AC が変わったら brainstorming に戻す）（`references/requirements-gating-steps.md` § Express）（`quick (express)` と判定した後、human check の往復で検出のパターンと AC が増えたのに sizing を保ったまま Options Exploration を飛ばし、検出範囲の過大と bot の制約の欠落がレビューで発覚した事例がある）。

13. `state.md` の `Gate Status` は初期値として次を入れる: `Requirements Review Status=pending` / `Design Review Status=pending` / `Human Check Status=pending` / `Resume From=gdd-brainstorming`。

14. **差し戻し追従更新**: planning の差し戻しで requirements を更新した場合は、requirements reviewer と human check に戻す前に、lightweight `design.md` skeleton の主要フロー / 影響範囲と、`Summary Brief` / `Design Policy Discussion` / `Human Check Questions`（該当時は `Route / Ownership Matrix` / `Sensitive Data / Masking Policy`）を追従更新する。`Summary Brief` の `外部依存の確認結果` も最新情報に合わせて取り直す。対象技術や version 前提が変わった場合は最新情報を取り直す。

15. **知見の棲み分け**: 調査した案・試して捨てた選択肢・検索過程など、artifact に残すほどではないがセッション跨ぎで失われると困る知見は `.steering/.../worklog.md` に追記してよい。`adr.md` は「決まったこと」、`worklog.md` は「過程」として棲み分ける（worklog は canonical state / routing source / gate 条件にはしない）。
    - 技術調査・比較検証・pre-workflow brainstorm の発見は `.steering/.../findings.md` に `Sources` / `Synthesized Findings` / `Comparisons (任意)` のセクションで構造化して残す（gate 条件・routing source にはしない）
    - **Findings 永続化ルール**: 調査操作（web 検索、ドキュメント読み込み、コード探索)を **2 回**行ったら、得られた知見を findings.md に書き出す。コンテキストウィンドウは揮発性の RAM、ファイルシステムは永続的なディスク — 長い調査で発見が失われるのを構造的に防ぐ。永続化のタイミングを逃しても gate 違反にはならないが、未永続化の調査結果に依存した判断があれば Self-Review で検出される

16. **Iterative Refinement Loop（自律解決）**: artifact の初稿が書けたら、Self-Review（Step 17）に進む前に以下のループで未解決事項を **AI が自律的に解決**する。ユーザーに質問して止まらない。ループは最大 3 回まで（3 回で収束しない場合は残りを `Open Questions` に明示して Self-Review に進む）。

    **16a. Gap Scan** — 次の観点で未解決事項を洗い出す: ①`未確定事項` に項目が残っている ②`Open Questions` に項目が残っている ③`受入条件` に曖昧な表現がある（「適切に」「必要に応じて」等、判定基準が不明なもの）④`Design Policy Discussion` の採用案に根拠が弱いもの、または非採用案との比較が不足しているもの ⑤`Human Check Questions` が未作成、または方向性承認を除いて 2 個を超え、理由の 1 行が無い（正本: `references/requirements-template.md` § 事実は AC に 1 回だけ書く）⑥該当する条件付き節（`Post-PR Completion Scope` / `Route / Ownership Matrix` / `Sensitive Data / Masking Policy`）が空のまま
    **16b. Self-Resolve** — Gap Scan で見つかった未解決事項を、ユーザーに質問せず AI が自律的に解決する: 利用可能なコンテキスト（既存コード、設定ファイル、ドキュメント）から判断材料を集める / `tech-docs-searcher` 等のツールで不足情報を補う / 十分な根拠があれば AI が判断を確定し、判断根拠を artifact に記録する / AI だけでは判断できない policy-level の事項（ビジネス判断、承認権限、組織方針）は `Human Check Questions` の承認ポイントに残す / 技術的に複数の合理的選択肢がある場合は最もシンプルな案を採用し `Design Policy Discussion` に判断根拠と非採用案を記録する / **ユーザーに質問して assistant turn を終了してはならない**（質問が必要な事項は承認ポイントとして HITL に集約する）
    **16c. Update** — Self-Resolve の結果を `requirements.md` と `design.md` に反映する: 確定した事項は `未確定事項` から `確定事項` に移し判断根拠を添える / 解決した質問は `Open Questions` から削除し本文の該当セクションに反映する / 設計判断が固まったら `Design Policy Discussion` の採用案/非採用案を更新する / 新たに判明した未確定事項があれば `未確定事項` / `Open Questions` に追加する
    **16d. Re-scan** — 16a に戻る。Gap Scan で未解決事項が 0 件（`Human Check Questions` に残した承認ポイントは除く）になったら Step 17 に進む

17. `requirements.md` と lightweight `design.md` が固まったら、以下の 3 点だけを素早くチェックする（既存のコード・テスト・数値との照合は、`gdd-requirements-gating` の Step 4a の提出前の照合で、別の agent が行う。ここでは 3 点だけを見る）: ①**Placeholder scan**（正本: `common-guardrails.md` § プレースホルダー禁止）: 禁止表現や未完成セクションがないか ②**Human Check Questions の品質**: 各承認ポイントが番号付きで、人間が artifact を開かずに判断できる粒度になっているか ③**Open Questions の残存レベル**: スコープ・方針レベルの未解決事項が残っている場合は Self-Review fail。実装詳細レベルは残してよい。問題を見つけたらその場で修正する。再レビューは不要。

18. Self-Review を通過したら `Resume From=gdd-requirements-gating` に更新する。タスクサイズ判定結果は human-check テンプレート（`references/human-check-template.md`）の「タスクサイズ」「フロー」行で明示する。
    **フロー表示の値**:
    - `quick (express)`: 要件整理 → 要件レビュー → 人間確認 → TDD → 実装 → 品質レビュー → 完了（設計・タスク分割・完了チェックはスキップ）
    - `quick (standard)`: 要件整理 → 要件レビュー → 人間確認 → 設計 → 実装 → 品質レビュー → 完了（専門レビュアはスキップ）
    - `standard`: 要件整理 → 要件レビュー → 人間確認 → 設計 → 設計レビュー → タスク分割 → TDD → 実装レビュー（専門レビュア含む） → 完了チェック

19. 選択肢が多く、かつユーザーが明示的に比較過程の保存を求めたときだけ `.cursor/plans/*.plan.md` を使う。

20. `gdd-requirements-gating` 通過後は `Resume From=human-check-waiting` で human check へ進む。出力テンプレートと停止ルールは SKILL.md § Output Guidance を参照。
