# 日本語文章規範（人間向け成果物用）

GDD が出す人間向けの文章（PR 本文、ADR、requirements / design の説明文）は、この規範に従って書く。
受入条件の検査とは違い、これは読みやすさのための助言であって、合否を機械判定する gate ではない。

## ルー語を避ける（最優先）

平易な日本語で言える概念を、英単語のまま地の文に挟まない。
難解な英単語が文の途中に入ると、読み手が意味を取れなくなる。

### 言い換え対応表（GDD 文書で頻出する語）

| 使いがちな語 | 日本語への言い換え | 備考 |

| marker | 目印 | |

| handoff | 引き渡し | |

| rollback | 切り戻し | |

| evidence | 証跡 / 根拠 | GDD 文書では「証跡」が多い |

### そのまま英語でよい語

- **コマンド・ファイル名・ツール名**: `git`, `gh pr create`, ファイルパス、スクリプト名など
- **GDD 固有の確立した術語**: SKILL, AC, PR, diff, commit, merge, gate（複合形でも英語のまま）, green / red（GDD 用語として定着）
- **業界標準の略語**: API, CI, URL, ID など

- どうしても英語術語が要るときは、初出に日本語の言い換えか注釈を括弧で添え、以後は片方に統一する。例:「エラー時は通す（fail-open）」。
- カタカナ語の乱用も避ける。意味が同じなら日本語の動詞や名詞を選ぶ。
- 悪い例:「root cause を特定し、workaround を apply する」
- 良い例:「根本原因を特定し、回避策を適用する」

## 読みやすさ

- 一文を短くする。一段落に一つのトピックだけを置く。
- 段落の最初の文を読めば、その段落の主題がわかるようにする。
- コード、差分、ログ、設定の断片はコードブロックで示す。
- 用語を初めて定義するときはその語を太字にする。太字の多用は避け、論理の要所に限る。
- 日本語の地の文と見出しでダッシュ（—, ―, ——）を使わない。補足は括弧に、言い換えは二文に分ける。
- 日本語の並列で中黒（・）を使わない。

## PR 本文

型の出典は plain-writing plugin の `writing-for-readers` skill の規則（rules.md）の § PR description で、GDD が PR を作るときに守る部分だけをここに写す（plain-writing の skill は呼ばない）。`references/post-completion-pr-flow.md` の各 Check は本文に要る中身を決め、置き場はこの型に従う。
PR テンプレートがあれば、その見出しに従う。各見出しの下は 1〜3 行にし、当てはまらない見出しは「なし」とだけ書き、テンプレートに無い見出しを足さない。当てはまる見出しが無い情報は末尾に 1 段落で足し、3 行を超えるときだけ短い見出しを付ける。テンプレートが無ければ、なぜ変えるか、差分を読んでもわからない挙動の変化、確認したこと（コマンドと結果を 1 行ずつ）、やっていないこと・残した問題、レビューで特に見てほしい箇所、の順に書き、項目名を見出しにしない（「確認したこと:」「やっていないこと:」の短いラベルは付けてよい）。 **残した問題の欄**は、テンプレートがあれば末尾の段落（後続対応の欄があればそこ。3 行を超えるなら `やっていないこと` などの短い見出しを付ける）、無ければ「やっていないこと:」のラベルの下を指す。 「実装内容」「変更内容」のような見出しにも、ファイルの一覧ではなく挙動の変化を書く。ファイルごとの変更一覧、行数、テスト名の羅列、工程の記録（gate の経緯、どの巡で何が出たか、試してやめた案）を書かず、同じ事実を 2 つの節に書かない。目安は、テンプレートの見出しと `指摘止まり（` の行を除いて 3〜15 行。

## LLM っぽい空句を使わない

論点を増やさず体裁だけ整える言い回しを使わない。

- 予告と総括:「重要なのは〜である」「本章では〜を扱う」「まとめると」
- 空虚な形容:「不可欠」「核心的」「鍵となる」「包括的」「多角的」
- 空虚な動詞:「掘り下げる」「言語化する」「触れる」
- 接続の型:「〜において」「〜の観点から」、「さらに」「また」の連打

主張はそのまま書く。確定していることは具体的に言い切り、不確実なことは不確実なまま書く。
