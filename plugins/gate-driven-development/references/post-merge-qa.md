# マージ後の QA（自走上限「マージまで」「マージ・デプロイ・QA まで」）
> **所有**: QA の範囲（本人が human check で承認する環境・デプロイ・書き込み先）、自走上限の 2 値の中身、QA 計画、マージ後の QA の手順の正本。**参照元**: `references/human-check-template.md` § 自走上限の置換値、`references/post-completion-pr-flow.md` Option 1 手順 7、`references/subagent-dispatch.md` § Completion-Check Post-Return Routing、`agents/gdd-qa-runner.md`、`skills/gdd-pr-review-followup/SKILL.md`（`Merge Approval`）、`skills/gdd-completion-check/SKILL.md`、`references/state-field-tiers.md`、`references/self-review-lanes.md` § merge gate 証跡、`references/fixed-models.md`

タスクの human check で本人が自走上限に `マージまで` か `マージ・デプロイ・QA まで` を選んだとき（本人の事前回答で選んだとき、承認の後に会話で引き上げたときを含む。`references/human-check-template.md` § 事前回答の 1・5）の手順である。どちらの値もどの repo でも選べる。QA の場所は原則として DEV・STG などの本番でない環境にし、本番しか無い repo では、§ QA の範囲に本番と書き込み先を並べて本人が選んだときだけ本番で行う。手順は main が実行する。

マージしてよいかを repo の側で止めるのは、GitHub の branch protection・ruleset・必須レビュー・CODEOWNERS である。セルフマージを許さない repo では GitHub がマージを断るので、GDD は repo ごとの宣言も、「必ず人が見るファイル」の判定も持たない（旧 `GDD Post-PR Autonomy`・`GDD QA *`・`GDD Human Review Paths` の行は廃止した。`.gdd-config.md` にあっても読まない）。GDD が守るのは、GitHub の拒否を回避しないこと（手順 2）と、GitHub が止めない QA の環境・書き込み先を本人の承認の中に閉じること（§ QA の範囲）である。

## 入口
- 条件（正本。post-completion-pr-flow.md Option 1 手順 7、Completion-Check Post-Return Routing、completion-check の Re-entry はここを指す）：Option 1 で PR を作り、`state.md` の `Approved Direction` の `自走上限`（下の読み方で読んだ値）が `マージまで` か `マージ・デプロイ・QA まで` で、同じ `Approved Direction` の `Post-PR Completion Scope` が無い（`none`・`なし` を含む）か、その項目がすべて自走上限の中にあること
  - 中にある項目は、マージ、デプロイの完了確認、QA 計画に入る確認（read-only か、§ QA の範囲の環境と書き込み先の中の書き込み）である。`マージまで` では、マージと read-only の確認だけが中にある。確認の項目は、QA 計画の手順か、`マージまで` では手順 2 のマージ後の read-only の確認に入れる
  - 外の項目（apply、release、§ QA の範囲の外への書き込み、外部への投稿など）が 1 つでもあれば、この文書に入らず Option 1 手順 7 の Post-PR Scope Continuation に進む
- 行と値の読み方（正本。手順 2 の本人の承認も同じ）：`state.md` 全体のコードフェンスの外で、先頭の空白・箇条の記号（`-`・`*`・`+`）・`**`・バッククォートを除いて `自走上限` で始まり、括弧の注記を挟んでもよく、その後に `:`・`：`・`=` が来る行を数える（`Human Check Status` も同じ数え方）。どちらも 1 行だけのときにその行を使い、`自走上限` は `- 自走上限: <値>` の形のときだけ使う。0 行・2 行以上、またはほかの形なら条件を満たさない。値は `references/state-machine.md` § state field のフォーマット検証のとおり、ラベルの後の `:` か `=` の後から最初の ` | ` の前まで（無ければ行末まで）を trim したもので、完全一致で比べる（括弧の補足などの注記を付けた値は、どの値にも当たらない）。evidence は ` | evidence:` の後から次の ` | ` の前まで（無ければ行末まで）を trim したもの
- 経路：runner が PR を作って `done` で戻ったら、main が Completion-Check Post-Return Routing から入る。completion-check を main で動かしたとき（Codex で委譲の許可が無いなど）は、Option 1 手順 7 からそのまま続ける。中断した後にユーザーが再開を頼んだら、`worklog.md` にあるこの文書の記録（QA の範囲・QA 計画レビュー・マージ前・マージ・デプロイ・QA。`マージまで` では `マージ前` の行から見る）を読み、記録の無い最初の手順から続ける（手順 3〜5 は `マージ・デプロイ・QA まで` のときだけ。`QA 計画レビュー:` の high か blocking が 0 でない記録は、記録の無いものとして扱う）。`マージ前` の行があって `マージ` の行が無ければ、`gh pr view <PR> --json state,mergeCommit,headRefOid` で分ける：MERGED で head が `マージ前` の head と同じなら `マージ` の行を書き、`マージまで` では手順 2 の最後の read-only の確認をして `done`、`マージ・デプロイ・QA まで` では手順 3 へ進む。OPEN なら自走せず、手順 2 を 1 問で問う形でやり直す。CLOSED、head が違う、読めない・失敗したときは報告して止まる。`QA 結果:` の行が `pass` でなく `revert PR:` の行が無ければ手順 5 の revert から続け、`revert PR:` の行があれば報告して止まる

## QA の範囲（タスク単位。本人が承認する）
- `マージ・デプロイ・QA まで` を選択肢に出す human check では、同じ確認に QA の範囲として次の 3 つを並べる。本人がこの値を選んだら（事前回答・会話での引き上げを含む）、承認を記録するときに `worklog.md` に 1 行ずつ書く。12 桁のアカウント ID を含む ARN と絶対パスは書かない（steering の書き込み検査に止められる）
  - `QA の範囲: 環境 <環境名。本番なら 本番>`
  - `QA の範囲: デプロイ <マージで動くデプロイ系の workflow のファイル名, ...>`（デプロイ系の定義は `references/post-completion-pr-flow.md` の PR Body Merge-Triggered Workflows Check。human check の時点では差分が無いので、変える予定のパスから見込みで並べる）
  - `QA の範囲: 書き込み <先と操作, ... | なし>`
- 各値は、本人のターンの発話（表示した human check への返事、事前回答の原文、1 問への答え）から読めるものだけを書く。main・委任先・QA 計画が値を補わない。事前回答・後続 Stage・再開などで本人が範囲を見ていないとき、読めない値は `不明` と書く。`不明` を含む範囲では、手順 2 で自走でマージせずに 1 問で問う
- 範囲を変えるのは本人だけである。QA 計画（手順 1）とそのレビューで範囲を広げない。範囲の外が要ると分かったら、計画に入れず、手順 2 で自走でマージせずに 1 問で問い、はみ出した分を並べる。本人が答えたら、その発話を `worklog.md` に書き、`QA の範囲:` の行を書き直す
- 範囲の行が無い・3 行のどれかが欠ける・同じ種類の行が 2 行以上あるときは、範囲が無いものとし、手順 2 で自走でマージしない

## 手順
1. **QA 計画**（`マージ・デプロイ・QA まで` のとき。マージの前）：`<Steering Dir>/qa-plan.md` に、判定（合格の条件と証拠の種類・強さ。対象の自己申告は証拠にしない）、手順（順番・コマンド・書き込み）、前提（QA で使う経路の権限・ツールが動くことを含め、コードで確かめた `file:line`）、誤読（合成の入力が本物と違う形で分岐する、など）と対策と確かめられないこと、上限（費用・時間と止める基準）を書く。12 桁のアカウント ID を含む ARN と絶対パスは書かない（steering の書き込み検査に止められる）
   - 環境は § QA の範囲の環境だけ、書き込みは § QA の範囲の書き込み先と操作の中だけにする。さらに、runner に書き込みを任せてよいのは、手順 2 の本人の承認を満たすときだけである（任せるのは手順 2 の承認に並べた操作だけ）。無ければ、QA は書き込みをしない計画にする
   - 計画は Agent tool の `subagent_type: Plan`・`model: opus`（Edit・Write を持たない。effort は main から継承されるので `worklog.md` に書く）で、会話を引き継がずにレビューする。Codex・Cursor では手順 4 と同じ別コンテキスト（read-only）で行い、起動できなければマージせずに止まる。渡すのは qa-plan.md と PR の差分の場所だけ。high か blocking が出たら直して、もう 1 回まで通す。結果は `worklog.md` に `QA 計画レビュー: head <sha> / high <n> / blocking <n>` と書き、2 回目でも残るなら止まる
2. **マージ**：`skills/gdd-pr-review-followup/SKILL.md` のマージの経路で行う（レビュー収束と merge gate の証跡はそちらが正本。`Merge Approval` だけ下の形で書く）。`マージ・デプロイ・QA まで` では、QA 計画のレビューが high 0・blocking 0 で、その head がマージする PR の head と同じ（違えばレビューを回し直す）で、QA 計画が § QA の範囲の中にあり、下の `list-merge-triggered-workflows.py` の一覧の `起動する`・`起動しうる` のうちデプロイ系の workflow がすべて § QA の範囲のデプロイに入ることも条件にする
   - 自走のマージの条件（followup・human-check-template・state-field-tiers・self-review-lanes はここを指す）：§ 入口の条件を満たし、本人の承認（§ 入口の読み方で `Human Check Status` の行が 1 行だけで、値が `approved`、evidence が `human:<自走上限の値>` で、その値が § 入口で読んだ `自走上限` の値と完全に一致する。バッククォート・全角コロン・括弧の補足などの揺れ、変更前の承認は満たさない。本人の事前回答を適用した承認〔`references/human-check-template.md` § 事前回答〕も同じ形で満たす）であり、`マージ・デプロイ・QA まで` では `worklog.md` の § QA の範囲の 3 行がそろって値に `不明` が無く、上の条件（`マージ・デプロイ・QA まで` のとき）を満たすこと。この手順の `<head>`（`list-merge-triggered-workflows.py`、QA 計画レビュー、`マージ前`・`Merge Approval` の head）は、`git fetch origin --quiet` の後の `gh pr view <PR> --json headRefOid` の値にし、`git rev-parse HEAD` と違えば自走せずに報告して止まる。マージは `gh pr merge <PR> --match-head-commit <その sha>` で行い、head が動いて断られたら別の方法で試さず、followup の Collect に戻る。`--admin`・`--auto` を付けず、`gh api` などで merge の API を直に呼ばず、既定ブランチへ直接 push しない。branch protection・ruleset・必須レビューなどで GitHub に断られたら（セルフマージを許さない repo）、別の方法で試さず、断られた理由と、人がマージするときのコマンドを報告して `<gdd-stop reason="blocked">` で止まる。人がマージした後に再開を頼まれたら、§ 入口の経路で続ける（デプロイの完了確認と QA は自走上限のとおり行う）。このときだけ `Merge Approval` を問わない。マージの直前に `worklog.md` に `マージ前: PR #<n> / head <sha> / 起動: <workflow と環境。本番なら本番> / QA の書き込み: <先と操作の全件 | なし>` と書き（アカウント ID を含む ARN と絶対パスは手順 1 と同じく書かない。`起動:` の workflow と、条件が欠けて 1 問で問うときに並べる workflow は、`git fetch origin --quiet` の後に `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/list-merge-triggered-workflows.py --base origin/<既定ブランチ> --head <head> --default-branch <既定ブランチ> --merge-with origin/<既定ブランチ>` で作った一覧の `起動する`・`起動しうる` の行。script が 0 以外で終わったら、`マージ前` の行を書かず、自走でマージせず、1 問でも一覧の無いまま問わずに、出力を報告して `<gdd-stop reason="blocked">` で止まる）、`state.md` の `## Gate Status` に `Merge Approval: PR #<n> / head <sha> | evidence: post-pr-autonomy:<自走上限の値> | approved_at: <ISO 8601>` の bullet を書く（`approved_at` は書いた時刻で、人間の承認の鮮度は測らない）。マージに成功したら `マージ: PR #<n> / merge commit <sha>` と書く（再開は § 入口の経路）。条件が 1 つでも欠ければ followup の経路どおり 1 問で問い、その問いに同じ全件を並べる。承認（自走では `マージ前` の行）が含むのは並べた操作だけである
   - merge gate は merge を止めない。不足があれば、merge の後に「実行後の通知」として reason code を返す。レビューの待ち（followup の Review Pending Loop）と証跡は、merge の前に main が確かめる。通知が出たら、承認や証跡を後から書き足さず、通知の reason code と不足をユーザーに報告して止まる。その他の hook の deny、auto mode classifier の拒否では、同じ操作を別の方法で試さず、拒否の理由・満たしていない条件・ユーザーが打つコマンドを出して止まる
   - マージを CI などの完了まで待つときは、Stop hook の cwd の toplevel（通常はセッションを起動した worktree。GDD の worktree で作業していてもこちら。Stop hook はここだけを読み、押し返しの文に絶対パスを出す。制御文字・surrogate を含むパスは `.claude/gdd-merge-intent.json` と相対で出す）の `.claude/gdd-merge-intent.json` に、Write ツールで `{"pr": <番号>, "repo": "<owner/name。省略可>", "then": "<マージ後の作業>", "original": "<許可の原文>"}` を書き、待つ仕組み（plugin の `scripts/wait-until.py --timeout <秒> --pr-checks <番号> [-R <owner/name>]` を Bash の run_in_background で。上限・終了コード・出力はスクリプトの docstring）を起動してから止まる。PR が OPEN のまま、宣言を書いたセッションが止まると、Stop hook が PR と CI の状態を添えて押し返すことがある（同じ状態のまま 2 回目に止まったら通す。Bash・ApplyPatch・subagent で書いた宣言、別のセッションが書き直した宣言、直前のターンが peer のとき、宣言を書いた後の同じ PR〔番号・URL で PR を特定できない形を含む〕の `gh pr merge` の最後の試行が、走る前に止められていたとき〔`Exit code` で始まらない is_error の結果。本文が空のもの、上の拒否を含む〕、押し返しの文を UTF-8 に encode できないとき、直近 2 時間 10 分に起動し、まだ終わっていない background の処理〔Bash・Agent〕があるとき、gh が答えないとき、締め切りを過ぎたときは押し返さない。`hooks/scripts/lib/autonomy_pushback.py`）。押し返しを当てにせず、待つ仕組みは自分で起動する。マージした・しないと決めたら宣言を消す。GDD の外のマージ待ちでも同じ
   - `マージまで` はここで終わる。マージ後の確認（Scope の確認の項目を含む）は read-only だけにして `done` にする
3. **デプロイの完了**：`gh pr view <PR> --json mergeCommit` の commit について、§ QA の範囲のデプロイの workflow のうち差分のパスで起動するもの（`git fetch origin --quiet` の後に `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/list-merge-triggered-workflows.py --base <push の前> --head <merge commit> --default-branch <既定ブランチ>`〔`<push の前>` の決め方は `references/post-completion-pr-flow.md` § Manual Merge Continuation の 1〕 の `起動する`・`起動しうる` の行。その行の、範囲に無い workflow のうちデプロイ系〔`references/post-completion-pr-flow.md` の PR Body Merge-Triggered Workflows Check の定義〕も同じように確かめる。ただし範囲に無い workflow の `起動しうる` の行は、run が 10 分たっても現れなければ `worklog.md` に `起動しなかった: <workflow>` と書いて止まらずに進む。script が 0 以外で終わったら、一覧の無いまま workflow を選ばず、出力を報告して `<gdd-stop reason="blocked">` で止まる）を `gh run list --workflow <名前> --commit <commit> --json status,conclusion,url`（理由が push でない行は、§ Manual Merge Continuation の 1 の探し方）で確かめ（run の出現・完了を待つときは `scripts/wait-until.py` の `-- <条件コマンド>` の形で、上限つきで待つ。workflow ごとに、出現・完了の順に別に起動し、条件を分けて書く。出現の条件は、その workflow の run が無ければ 1、あれば 0。完了の条件は、status が `waiting`（環境の承認待ち）の run があれば 3、終わっていない run があれば 1、全部終わったら結論を問わず 0。どちらも gh が失敗したら 2 以上を返す。出現は `--timeout 600` で、完了は QA 計画の時間の上限で待つ。上限が 7,200 秒を超えるときは 7,200 秒で起動し、124 で終わったら run の状態を確かめてから残りの時間で起動し直す）、run がすべて success のときだけ `worklog.md` に `デプロイ: <run の URL と結論>` と書く（それ以外は書かずに下のとおり止まる）。run が 10 分たっても現れない、失敗した、環境の承認待ちになった、または QA 計画の時間の上限を超えたら、revert の PR は作らず（途中まで出たデプロイは revert で戻るとは限らない）、run の URL と状態を報告して `<gdd-stop reason="blocked">` で止まる
4. **QA**：`subagent_type: gate-driven-development:gdd-qa-runner` で起動する（model は渡さない。agent 定義で `opus`・`effort: high`）。prompt には qa-plan.md のパス、マージ commit、§ QA の範囲で記録した `QA の範囲:` の 3 行を書く。定義が読み込まれていないセッションでは `general-purpose` を `model: opus` で起動して定義の本文を渡し、effort を継承したことを `worklog.md` に書く。Codex・Cursor では `references/fixed-models.md` の `general_heavy_risk` tier の別コンテキストに本文を渡す。Codex は `references/codex.md` § Codex Subagent Delegation Permission の許可が無ければ QA をせずに止まる。runner が戻ったら、すぐに `worklog.md` に `QA 結果: <pass | fail | inconclusive>` と書く。ツールを絞れないときは、read-only が散文だけになったことを `worklog.md` に書く
5. **結果**：`pass` なら結果と証拠を `worklog.md` に書いて `done` にする（`done` の直前に `references/post-completion-pr-flow.md` Step 4 の `記録の場所: なし` の行を書く。2 の `マージまで` の `done` も同じ）。`fail` か `inconclusive` なら revert の PR を作るところまで行い（マージはしない。作ったら `worklog.md` に `revert PR: <URL>` と書く）、QA の結果・revert の PR・影響を報告して `<gdd-stop reason="blocked">` で止まる。revert は、既定ブランチから steering の無い別の worktree（`skills/gdd-using-git-worktrees/SKILL.md`）で作る。merge commit・squash・rebase の見分け方は `references/post-completion-pr-flow.md` § Manual Merge Continuation の 1 の `<push の前>` の決め方による。merge commit なら `git revert -m 1 <commit>`、squash なら `git revert <commit>`。rebase merge で commit が複数あるとき、または pre-push・pre-PR gate の実行後の通知を受けたときは、escape hatch（`GDD_SKIP_PRE_PUSH_GATE` など）で通知を消さず、作られた revert の PR の URL（作っていなければ revert のコマンド）と通知の不足を報告して止まる。fail の原因が、人が手で入れた値の形（secret の登録の形・フォームの入力など）とコードの読み方の食い違いなら、報告の推奨は `references/common-guardrails.md` § 選ぶときの基準 の 8 に従い、人に入れ直させる案を推奨にしない

## 限界
- 許可外の書き込みを止める hook は無い。守らせるのは、本人が承認した QA の範囲、QA 計画のレビュー、`agents/gdd-qa-runner.md` の規定だけである。QA を Opus で行うことを保証するのも agent 定義の frontmatter だけである。dispatch gate は QA の起動を QA として判定しない（tasklist.md に残る前の工程の判定が当たることはある。`general-purpose` の経路では model の明示だけが頼りになる）
- merge gate は自走の承認と人間の承認を区別せず、`Merge Approval` を誰のターンで書いたかも見ない（別セッションの直後の書き込みは、steering の書き込み検査が止める。Edit・Write などのツールで書いたときだけで、Bash で書いたときは止めない）。QA の範囲・自走上限・QA 計画レビューの条件と、GitHub の拒否を回避しないことを守らせるのは main の手順だけである。エージェントが `worklog.md` に記録の行を書いても、`Human Check Status` の evidence を同じセッションで書き換えても、止める hook は無い。`human:` の evidence を新しく書くのは本人のターンの承認と、事前回答の適用（`worklog.md` の `事前回答:` の行を `references/human-check-template.md` § 事前回答 2 のとおり確かめたもの）の記録だけだが（`approved` のまま書き直すときは元の evidence を写す。`references/gate-status-schema.md`）、main がそれ以外のターンで書いても止める hook は無い（別セッションのターンの書き込みを peer turn の書き込み検査が止めるのは、Edit・Write などのツールで書いたときだけで、Bash で書いたときは止めない）。「1 行だけ」も main が数える。委任先が `human_recheck_required` を承認しても evidence は `human:<自走上限の値>` のままで、マージは 1 問で問う側に戻らない（自走上限の値は本人が選んだもので、それより先へ進むのは § 事前回答 3 が止める）。利用者の規則（グローバルの CLAUDE.md・AGENTS.md）は読まない。repo の側で自走のマージを止めるのは branch protection・ruleset・必須レビューだけである。保護の無い repo では、workflow・CODEOWNERS・`.claude/settings.json` を変える PR も、本人が上限を選べば自走でマージされる。管理者が保護を越えられる設定（enforce_admins が off、ruleset の bypass）の repo で、gh の通常のマージが断られるかは未測である。auto mode classifier は自走のマージを拒否することがある。本番しか無い repo では、マージがそのまま本番デプロイになり、止めるのは human check に並べた workflow と環境（判定できなければ `不明`）と本人の選択だけである
- `/gdd-dev` を使わないセッションには届かない
