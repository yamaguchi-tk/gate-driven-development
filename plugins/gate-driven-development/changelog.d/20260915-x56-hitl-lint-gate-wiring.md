#### Summary

（この断片の後の `20261014-hitl-lint-warn-only.md` で、lint を通らない HITL を差し戻すのをやめ、警告と記録だけにした。差し戻しの予算 `hitl_lint_blocks` も外した。以下の差し戻し・予算の記述は、その前の挙動である）

HITL（`<gdd-stop reason="human-check-waiting">`）向けの品質lintは6本存在し判定ロジックは正しく動くが、呼び出し手順が散文の参照ドキュメントにしか書かれておらず、実運用でほぼ実行されていなかった（実測: 271 session 中 HITL 表示があった session のうち lint を実行したのは 6 件 = 2%）。これは「規定を書いただけで発火点を登録していない」典型的な失敗であり、本 PR ではこの構造そのものを直す。既存 lint の判定ロジックは一切変更せず、そのうち 3 本（lint-hitl-display-integrity / lint-human-check-language / lint-hitl-complexity）を `gdd_stop_hook.py` の `human-check-waiting` 経路から自動実行するよう配線した（X-56）。

#### Added

#### Known limitations

- v1 で配線するのは 6 本中 3 本のみ。残り 3 本（lint-hitl-decision-quality / lint-hitl-stage-plan / lint-hitl-outcome-audit）は、既存の判定ロジックを変えずに全 HITL へ一律適用すると誤検知や適用範囲外テキストへの適用になるため対象外とした（詳細は `hooks/scripts/lib/hitl_lint_gate.py` のモジュール docstring を参照）
- **実測した block 率は非常に高い**。有効化前に、リポジトリ内の実際の HITL 本文サンプル 6 件（`tests/fixtures/gdd-scenario-eval-inputs/hitl-decision-packet-ac1-where-full.assistant.md` / `hitl_option_verification_plan.assistant.md` / `tests/fixtures/e2e-replay/*/final-hitl.md` 4 本）に配線済み 3 本を実測でかけたところ、**6 件中 6 件すべてが display-integrity と human-check-language の両方で fail**した（complexity のみ全件 pass）。今回新規作成した gold-pass fixture 以外に、この 3 本を同時に通す実例はリポジトリ内に存在しない。block-once-then-allow（workflow あたり既定 2 回まで差し戻し）を選んだのはこの高い fail 率を見越した設計であり、これにより実運用での恒常的な block は避けられるが、裏を返すと「human-check-waiting のたびに最大 2 ターンの遅延が起き、その後は結局 allow される」に収束する可能性が高い。将来の対応候補: (a) display-integrity の要求（15 マーカー全一致）を緩めるか、(b) v1 を complexity 1 本に絞るか、(c) 現状のまま「数ターンの自己修正機会」自体を価値と見なすか。既存 lint の判定ロジックを変えない本 PR のスコープでは判断せず、実測値のみ記録する
- **予算（既定 2）は workflow 全体で共有され、HITL の出現箇所ごとにリセットされない**。1 箇所（例: 要件 HITL）が不良のまま 2 回連続で出ると予算を使い切り、後続の別箇所（例: 設計 HITL）では nudge が一切飛ばずに即 allow される。reset 経路を持たない設計（下記）とのトレードオフとして受け入れる——「識別子に依存して cross-session 干渉を起こす」より「稀に後続フェーズの nudge 機会を失う」方が実害が小さいと判断した（設計アドバイザリ, 2026-09-15）。予算の上限は `hitl_lint_gate.HITL_LINT_BLOCK_BUDGET` で調整可能
- Stop hook が `human-check-waiting` に到達する経路は 3 つあるが、`last_output` に HITL マーカーが文字列として存在する経路（主経路）だけを採点する。tool_result 側にのみマーカーがある経路（`gdd_stop_hook.py` の `_check_stop_markers` 内、tool_result 一致 かつ `last_output` 側にはマーカー無し）と、`state.md` からの markerless fallback 経路は採点対象外。前者は皮肉にも display-integrity lint 自体の動機（subagent が生成した HITL を main session が再要約し「ズレ確認」等を落とす事故）と同一の形であり、その経路にこそ display-integrity が届いていない。マーカー一致集合自体は対称（`STOP_PATTERN` は両経路で同じ）だが、「どちらの経路を採点するか」が非対称になっている。修正には、tool_result 一致経路で `last_output`（実際の表示面）を採点しつつ marker-missing 自体は failure から除く、という設計判断が要り、既存判定ロジックを変えない配線のみという本 PR のスコープを超えるため次回対応とする
- `human-check-waiting` 以外の pause reason（例: `clarification-needed`）は `_stop_for_non_done_reason` で同様に人間へ到達するが採点対象外。block reason は「もう一度 `human-check-waiting` を出力してください」と指示するのみで、reason を差し替えて停止すること自体は防いでいない。実際にどの程度使われるかは次点のテレメトリ課題と合わせて計測が必要
- ゲートの実効性（block / allow / give-up の発生頻度）を測るテレメトリは未実装。block だけが `decision.reason` の文字列として transcript に残り事後計測できる一方、pass と「予算を使い切って allow した」瞬間は完全に無記録。X-56 自体が「実際に実行されているか」を transcript 走査でしか確認できなかった教訓を踏まえると、次点でこのゲート自身の発火実績を計測できる記録を残すことが望ましい
- `hitl_lint_gate.py` の `_resolve_plugin_root()` は `gdd_stop_hook.py` の `_read_hook_input()` と同じ解決ロジック（`CLAUDE_PLUGIN_ROOT` → `GDD_PLUGIN_ROOT` → `cwd`）の重複であり、`main()` が常に `plugin_root` を渡すようになった今は実運用では通らない（unit test 経由のフォールバックとしてのみ生きている）。DRY 違反であり次点で共通化を検討する
- `.claude/gdd-dev.local.md` 自体は `/gdd-dev` 起動時に `setup-gdd-loop.sh` が無条件に作り直すため、`hitl_lint_blocks` の予算は `/gdd-dev` を再起動するたびにリセットされる（独立レビュー4巡目 finding 1）。人間の能動的操作 1 回につき予算 1 回分のリセットに留まり、他 session の日常動作を契機に自動で消えることはないため 1〜3 巡目の実害クラスには当たらないが、運用上は「`/gdd-dev` を頻繁に再起動する運用では block-once-then-allow が実質的に無効化される」ことを認識しておく必要がある
- `consume_hitl_lint_block_budget` は `prompt_body` が空文字で渡された場合にそのまま `write_state` してしまい、`.claude/gdd-dev.local.md` の本文（GDD の継続コンテキスト）を消しうる（独立レビュー4巡目 finding 4）。現在の呼び出し元は必ず正しい `prompt_body` を渡すため実害はないが、次点で `prompt_body` を必須引数にするか、空文字での上書きを拒否する防御を検討する
- main-text マッチと tool-result マッチが同一 Stop hook 呼び出しの中で二重に予算を消費しないことは、`_emit_block`/`_stop_for_non_done_reason` が必ず `SystemExit` で抜けることに依存しており、コードを読んで確認済みだが、これを直接ピンするテストが無い（独立レビュー4巡目 finding 5）。将来どちらかが例外を投げずに値を返すようリファクタされると気づかずに壊れる。次点でHITLマーカーを `last_output` と tool result の両方に含むe2eテストを追加する
- `.claude/gdd-dev.local.md` への書き込みは read-modify-write であり、`write_state` は frontmatter dict 全体でファイルを再構成する全体上書きである。そのため同一 `project_root` に対して Stop hook のプロセスが 2 つ同時に走ると、後に終わった側が起動時スナップショットでファイルを上書きし、その間に別プロセスが書いた `hitl_lint_blocks` を消しうる（並行 lost update、人間 PR レビューで指摘）。Claude Code runtime では `_session_guard` が state 側 `session_id` と一致しない session を早期 exit させ、Stop hook も SubagentStop には登録されていないため、この経路は構造的に発生しない。`session_id` が常に空になる Cursor runtime で、同一ディレクトリを 2 つのセッションが同時に走らせた場合にのみ成立する。1 回の lost update の影響は「予算が最大 2 回分戻り、余分な差し戻しターンが発生する」ことに留まるが、Cursor の 2 セッションが継続ループとして毎ターン重なって書き合う場合は、増分のたびに消えることが繰り返されうるため、HITL の予算が 2 に到達せず差し戻しが連続しうる（1〜3 巡目の High のような、別 session の正常系が確率 1 で毎回消費済み状態を消す設計ミスではなく、あくまで「Cursor・同一 project_root・両セッションとも Stop hook の継続書き込みまで進む」という条件が毎ターン揃った場合に限る）。block は必ず自プロセス内で予算を消費してから行われ、予算チェック自体は独立して動き続けるため、恒久的に allow できなくなることはない（恒久的に不都合な場合は `GDD_SKIP_HITL_LINT=1`）。なお、この lost update は本 PR で導入されたものではなく、同じ frontmatter に載る既存の `iteration` / `consecutive_stop_hook_blocks`（連続 block 上限カウンタ）/ `detected_phase` にも同条件で起きる。`hitl_lint_blocks` だけを個別に保護すると受理集合が非対称になるため、`.claude/gdd-dev.local.md` frontmatter 全体の並行更新契約（書き込み直前の再読込 merge、または単調キーの max 採用）として後続課題で一括対応する
