#### Known limitations

- **今回実装したのは4方針確認のうち「中間: 該当なし明記 + Option必須」のみ**。方針確認で「中間: standardは判断ポイント必須化」を選んだ「HITLの必須『中核項目』をどこまで広げ、どのsizingに適用するか」という軸は、本 PR のスコープでは実装していない（既存の17 Required Words のうちどれを「中核」として機械検査対象に格上げするかの選定と、sizing 別の適用範囲決定が別途必要なため）。今回追加したのは条件付き4節の該当なし明記と Option 軸の2点に限る。後続 PR で対応する
- **warn-only であり block しない**。新しい lint は fail するたびに `.gdd/hook-errors.log` に記録されるだけで、human-check-waiting の pause 自体は妨げない。実際の fail 率を実測してから、既存の3本と同じ block-once-then-allow 方式への昇格を別途判断する（ユーザー確認済みの方針）
- **X-56 と同様、リポジトリ内の既存 HITL サンプルの多くが新しい lint に fail する見込みが高い**（X-56 の3本でも実測6件中6件が fail していた前例がある）。本 PR では新規 lint を実際の既存サンプルに対して回帰的に計測していない（warn-only のため block による影響はないが、`.gdd/hook-errors.log` への記録量は当面多くなる可能性がある）
- `_is_substantial()` は「12文字以上の可視文字」という固定閾値で実質的な内容の有無を判定する。この閾値より短いが実質的な内容（例: 短い技術用語1つ）を誤って「空」と判定する可能性は残る。誤検知が実測されたら閾値を調整する
- `lint-hitl-required-fields.py` の CLI 引数（ファイルパス）は他の全 lint-*.py と同じパターンで `pathlib.Path` に渡している。Snyk のコード scan で Low severity の Path Traversal（CWE-23）として検出されたが、ローカル CLI ツールが呼び出し元の指定したファイルパスを読むのは意図した挙動であり（`lint-hitl-decision-quality.py:775` を含む既存の全 lint スクリプトが同じパターン）、信頼境界を越える実害はないと判断し対応不要とした
- **full template（`references/human-check-template.md`）・`gdd-requirements-gating` skill は、本 PR で compact に加えた「条件付き4節の常時表示化」に追随していない**（full 側は `アーキテクチャ選択` が bold 小見出しのままなど）。一次表示の正本を compact に揃えるか、機械検査の対象を compact 準拠 HITL に限ると明記するかは別途方針決定が必要なため、本 PR のスコープでは対応せず後続課題とする（PR 旧#92 レビュー指摘）
- `_run_and_log_warn_lints()` は warn 対象 lint の finding を1件ずつ `.gdd/hook-errors.log` に記録する。現状 `HITL_LINT_WARN_SCRIPTS` は1本のみのため実害は無いが、将来 warn 対象を増やす場合は `gdd-status` の末尾表示窓（直近5件）を占有しうる。lint 単位で1行に集約するか専用ログに分離するかは、warn 対象が増える時点で判断する（PR 旧#92 レビュー指摘）
- `_section_after()` の末尾定型行 `条件付き詳細: ...` の境界検出だけは見出しアンカー化されておらず、行頭アンカーなしの部分文字列一致のまま残っている。条件付き節の回答本文が偶然「条件付き詳細」という文字列で始まる文を含むと、そこで打ち切られる可能性が理論上残る（独立レビュー2巡目、advisory、実機未再現）
- 同じ見出し（例: `### アーキテクチャ選択`）が文書内に複数回出現した場合、常に最初の出現だけを節本体として扱う。1つ目が未編集 placeholder のままで2つ目に正しい回答があると reject 方向に誤判定する（独立レビュー2巡目、advisory、実機未再現、fail-open ではなく false-reject 方向）
- **（PR後-2、4巡目の再発を受けた設計見直し）placeholder の角括弧だけを取り除いた回答は、依然として合格しうる**（Opus 設計レビュー H-3、実機で再現確認済み）。`_conditional_section_errors` の内容チェックは、na_phrase が行頭に無くても `_is_substantial`（12文字以上の可視文字）を満たせば合格する設計のため、placeholder の説明文から `<`/`>` だけを除去した文字列（例示として長い自由文を含む）は、na_phrase の行頭アンカー化だけでは reject できない。この経路を閉じるには「未編集の説明文かどうか」を判定する仕組み自体が要り、本 PR の scope（(A) 最小修正）には含めていない。根本対応（`<gdd-hitl-fields options="none" ...>` のような宣言フィールド化、Opus 推奨の (B)）は後続タスクとして切り離した
- 見出し・境界検出（`_heading_pattern` / `_HEADING_LINE_RE`）はフェンス（```` ``` ````）を認識しない。4節すべてをフェンス付きコードブロックの中だけに置いた文書は誤って「節あり」と判定され合格する（PR後-2 指摘、GitHub レビューで実機再現済み）。フェンスマスキングの追加は Opus 設計レビューで「この PR の scope に対して複雑さに見合わない」と判断され、本 PR では対応せず後続課題とした
- インデント（4スペース）によるコードブロック、および `> ### 見出し` のように blockquote で引用された見出しは、フェンス同様に見出し・境界検出の対象外として想定していない（未検証・実機未再現）。実害が実測されたら個別に対応を検討する
- na_phrase・固定句の判定は「行頭が固定句の文字列で始まるか」（prefix 一致）だけを見ており、`理由: ）`のように理由部分が空のまま閉じ括弧だけ書いても合格する（PR後-2 指摘、実機再現済み）。closed-form の設計方針（自由文の内容は一切解釈しない）どおりの意図的な限界として受け入れ、理由の非空性・妥当性までは検証しない
- **本 PR で見送った「placeholder の完全一致比較 + フェンスマスキング」による全面改修**: 4巡目の再発を機に、上記の角括弧除去バイパス（H-3）とフェンス問題を一括で閉じる再設計を検討したが、Opus のセカンドオピニオンで「完全一致比較は placeholder への1文字の編集（誤字修正等）で現状 reject の入力が誤って pass に反転する新たな fail-open を持ち込む」「テンプレートからの実行時抽出が失敗した場合に空文字列へ静かに fallback するとそれ自体が新しい fail-open になる」と指摘され、実装しないことにした（方針メモ、review-log 参照）。この4回目の再発は、既存の除外ヒューリスティックへの個別パッチではなく「該当なし明記・Option ラベルの受理判定自体を、可視テキストのどこでも一致する substring-anywhere から行頭アンカー方式へ変える」という設計変更（本 PR の (A)）で対応した。宣言フィールド化（(B)）は、除外ヒューリスティックの精度に一切依存しない構造的な解決だが、`hooks/scripts/lib/constants.py` の `STOP_PATTERN` が `<gdd-stop reason="...">` の閉じ引用符の直後に `>` を要求する形で固定されているため、新しいマーカータグ（`<gdd-stop reason="...">` への属性追加ではなく別タグ）を要する設計になる見込みで、別 PR の後続タスクとする
