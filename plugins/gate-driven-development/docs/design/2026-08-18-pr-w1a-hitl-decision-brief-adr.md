# ADR: PR-W1 対話UX（design-gating で確定した判断）

記録日: 2026-08-16 / phase: gdd-design-gating / Design Revision: D2

`Approved Direction` が AI に委譲した「中間判断（検証閾値の確定、lint バジェット数値、分割線）」の範囲で確定した判断を残す。AC の追加・削除・意味変更は行っていない。

## ADR-W1-1: scenario eval の合格判定を baseline 比較に切り替える

- **Context**: `requirements.md` § Execution / Evaluation Reality は「本 PR の合格根拠は `--require-release-pass`」としていた。design-gating で実測したところ、`run-gdd-scenario-evals.py` は 53 scenario 中 48 件が fail（捕獲済み入力が 5 scenario 分しかないため）で、`release_decision()` は failed が 1 件でもあれば fail を返す。scenario 絞り込みオプションは無い。
- **Decision**: 合格判定を「(1) `--baseline-summary` に対する `comparison.degrade` が 0 件、(2) 新規 5 scenario の critical checklist がすべて pass、(3) それを新規契約テストが summary JSON から機械検査」に確定する。
- **Why**: 「fixture 全体の release pass」を根拠にすると、本 PR と無関係な 48 scenario の捕獲が終わるまで永久に赤で、LLM 挙動検証の打ち切り 5 回をここで空費する。AC-V-1 が要求する実体（新 scenario の存在 / critical checklist / 実行捕獲 / 決定論採点 / 退行なし）はすべて維持される。
- **Consequences**: 変更前に baseline summary の取得が必須になる。既存 48 fail の解消は本 PR の Non-Goal（別作業単位）として残る。

## ADR-W1-2: display-integrity のマーカーを content word で定義する

- **Context**: 現行 `REQUIRED_MARKERS` は `### 30秒判断` のように見出し装飾を含み、13 件のうち 5 件はどの正本テンプレートにも存在しない。実際の HITL 出力は `**なぜやるか（WHY・根本原因）**:` のような bold ラベル形式で、compact テンプレート自身が「見出し名は多少変えてよい」と明記している。
- **Decision**: マーカーを装飾なしの content word（例: `なぜやるか`）で定義する。テンプレート fence から自動導出する案は採らない。あわせて AC-W2-4 の契約テストを双方向（マーカー→正本の実在 / compact テンプレートの必須見出し→マーカー被覆）にする。
- **Why**: 装飾込みのマーカーは契約より厳しく、合成 fixture でしか pass しない lint を生む（= 現在の壊れ方の再生産）。自動導出は正規化規則自体が新たな暗黙契約になり、fence 内の記入欄との切り分けが不安定。双方向検査は「正本にある表示要素を lint が守っていない」という実際に起きた向きの事故を塞ぐ。
- **Consequences**: `lint-hitl-decision-quality.py` / `lint-human-check-language.py` も同じ語彙へ再同期する必要がある（AC-W2-4 の範囲内）。

## ADR-W1-3: AC-W2-7 の「保護の純減禁止」を、写像ではなく削除記録として履行する

- **Context**: 当初案は現行 13 マーカーをすべて新セットへ「写像」し、削除 0 件と宣言していた。実測では 5 件が full / compact のどちらにも存在せず、保護実績がゼロだった。
- **Decision**: 保護実績ゼロの 5 件は「削除」として扱い、1 件ごとに削除理由（全正本に不在・実測方法つき）と代替検査（写像先マーカー + 双方向検査）を `requirements.md` に記録する。`ズレ確認` 配下の 4 語は any-of 群へ緩和し、これも記録対象にする。
- **Why**: 存在しなかった保護を保護として台帳化するのは実質を偽る行為で、記録義務を回避する方向のインセンティブが働く。4 語の全件必須は「該当しない欄も並べる」網羅の証明型 HITL を lint 側から強制し、W-2 の目的と逆行する。
- **Consequences**: `requirements.md` に AC-W2-7 記録欄の追記が実装タスクの成果物として増える。契約テストはその記録の存在も検査する。
- **一部撤回（2026-08-16 / ADR-W1-10）**: 本 ADR の「削除 5 件 + 緩和 1 群」という区分は、`### 初期案・壁打ちから変わったこと`（壁打ち差分）を「`ズレ確認` へ統合」として保護済み扱いにしていた点が誤りだった。実測では当該要素の検査が完全に消えており（OLD rc=1 / NEW rc=0）、AC-W2-7 が禁じる保護の純減に該当する。区分は ADR-W1-10 の「削除 5 / 保持 1 / 緩和 6 / 維持 1 = 13」へ置き換える。

## ADR-W1-4: HITL 行数バジェットは Python を正本にし、テンプレートには導出値を残す

- **Context**: 数値をテンプレートから消して参照案内文だけにする案があったが、compact テンプレートは HITL を生成する LLM が読む一次正本である。また compact の雛形ブロックは現状で非空 31 行あり、目安「standard 30 行」は骨組みだけで超過する達成不能な数値だった。
- **Decision**: `scripts/lib/hitl_budget.py` を正本にし、テンプレートには導出値（数値）を 1 行で残して契約テストで一致を検査する。`PRIMARY_SURFACE_MAX_LINES["standard"]` を 30 → 45 に改め、hard 上限 `HITL_SAMPLE_MAX_LINES` は requirements 時点の確定値 60 を維持する。
- **Why**: 数値を消すと実行時プロンプトから行数指示が失われ、指示品質が落ちる。達成不能な目安は守られないまま形骸化する。45 + 承認ポイント 5 件分（+10 行）でも hard 上限 60 に収まる。
- **Consequences**: 最小準拠サンプルの実測が 45 を超えた場合は実測値 + 5 に更新して `worklog.md` に記録する。60 を超える場合は上限を上げず compact 雛形を短くする。

## ADR-W1-5: express runtime profile の純増を 0 以下にする

- **Context**: blocking check の実測残枠は express template lines +2 行、express estimated tokens +10（≒ 0.4 行）しかない。本 PR は express profile の 4 ファイルを触る。

- **Why**: 黙って上限を緩めるのは AC-W2-7 が禁じる「lint を弱めて通す」と同型で、本 PR の趣旨に反する。
- **Consequences**: 実装は差分ごとに `lint-runtime-budget.py` を実行して before / after を記録する必要がある。

## ADR-W1-6: 1 ターン 1 問を機械可読マーカーで検査する

- **Context**: `AskUserQuestion` は questions 配列に複数問を渡せるため、`contains_all` ベースの checklist では 4 問まとめて聞いた出力も pass する。ADR-4（2026-07-13〜14）は同種の判別力不足で 5 回連続失敗している。

- **Consequences**: 新語彙 `#### Q1` が Intake Interview の表示契約に加わる。捕獲採点はこのマーカーに依存する。

## ADR-W1-8: D-4（express 純増 0 以下）は承認済み scope では達成不能と実測で確定し、上限の扱いを human check に返す

記録日: 2026-08-16 / phase: gdd-systematic-debugging（T-4 Step 2〜3 適用後の blocking budget 超過） / route: human_recheck_required

- **Context**: T-4 Step 2（lint-hitl-display-integrity.py のマーカー再同期）と Step 3（compact への ズレ確認 追加）を適用した時点で、blocking check が 2 件落ちた。express template lines 187/186（+1）、express profile estimated tokens 33481/33468（+13）。全 37 check の failure は baseline 1 件（grade-evals）から 4 件へ増加。当初仮説は「tasklist の順序が設計方針（不要欄を消してから追加する）と逆で、追加が先・削除が後だから」だったが、design.md § Runtime Budget Plan の相殺見積りを tasklist の実テキストで測り直した結果、**終端状態でも超過する**ことが確定した（明細は design.md § D-4 実測検証）。計画差分の合計は +1367 chars（上限 +343 tokens）で、残枠は +10 tokens = 40 chars。express template lines も終端 188 > 186。standard profile も 57246 > 57132 で同様に超過する。
- **Decision**: **D-4 をエージェント判断で撤回しない**。上限値 186 / 33468（および standard 57132）の引き上げは D-4 の撤回にあたり、blocking guard を緩める行為なので、承認ポイント A として human check に返す。選択肢・帰結・無回答時のデフォルトは state.md § 承認ポイント A を正本とする。**Before**: `--max-express-template-lines 186` / `--max-express-estimated-tokens 33468` / `--max-standard-estimated-tokens 57132`（tests/checks/skill-body-budget.sh と tests/checks/lint-scripts-functional.sh に各 1 箇所ずつハードコード）。**After（承認された場合にのみ適用する候補値）**: 188 / 33801 / 57246。導出は baseline 実測値 + 計画差分の実測 chars を ceil(chars/4) でファイル単位に切り上げた上限（33458 + 343 = 33801、56903 + 343 = 57246、76 + 112 = 188）で、裁量パディングを含まない。承認された場合は T-26 で実測終端値まで ratchet down する。
- **Why**: Approved Direction は「lint バジェット数値」を中間判断として委譲しているが、D-4 は design-gating で明文化された「express を太らせない」という設計不変条件であり、その撤回は委譲された数値調整の域を超える。加えて本 PR の AC-W2-7 が「lint を弱めて AC を満たす解は不合格」と定めており、同じ PR の中で別の blocking guard を黙って緩めるのは自己矛盾になる。実際、上限値の書き換えは auto mode classifier にも deny された（2026-08-16、tests/checks/lint-scripts-functional.sh の編集）。エージェント側で押し通さず人間判断に返すのが正しい扱い。
- **Consequences**: (1) 本 phase では上限値を一切変更していない。blocking check は skill-body-budget と lint-scripts-functional の 2 件が RED のまま human check に入る（grade-evals は baseline）。これは欠陥の隠蔽ではなく、承認判断の材料として残す。(2) T-4 の Step 4（fixture 更新）と Step 5（AC-W2-7 台帳）は本 phase で完了済みで、承認後に再開する残作業は Step 3 起因の budget 解決のみ。(3) 承認内容によっては T-8 / T-9 / T-10 / T-13 / T-26 の Steps を design_detail_only で書き換える必要がある（tasklist coverage gap 3 件は design.md § D-4 実測検証 末尾に列挙）。(4) ADR-W1-5（D-4 の起票 ADR）は本 ADR により「実測で前提が崩れた」状態になる。撤回するか維持するかは承認ポイント A の結果で確定する。

## ADR-W1-9: 承認ポイント A（A-1）の適用結果を確定し、D-4 を撤回して D-7（1 回限りの引き上げ + T-26 で ratchet down + per-task 文字数バジェット）へ置き換える

記録日: 2026-08-16 / phase: gdd-design-gating（D4） / route: design_detail_only

- **Context**: 承認ポイント A に対しユーザーが **A-1** を選択し、メインセッションが上限を引き上げて適用した（express template lines 186→188 / express tokens 33468→33801 / standard tokens 57132→57246、いずれも tests/checks/skill-body-budget.sh と tests/checks/lint-scripts-functional.sh の各 1 箇所）。あわせて `tests/test_reference_integrity_contract.py:113` の compact テンプレート行数上限を 110→112 に引き上げた。**この 4 件目は承認ポイント A の選択肢一覧に列挙されていなかった**。さらに外部要因として、並行セッションが v0.27.1 を main にマージし本 branch が追従した結果、base 時点の既存 failure 2 面（grade-evals / test_versioning_uses_manifest_version_and_mentions_codex_release_sync）が main 側で解消され、baseline が「失敗 0 件 / pytest 865 passed・0 failed・1 skipped」に変わった。
- **Decision**: (1) **D-4（express profile の純増 0 以下）を正式に撤回**し、design.md § D-4 の撤回と新しい制約（D-7） を新しい正本制約とする — 上限引き上げは今回の 1 回限り / T-26 で実測終端値まで ratchet down する / 残り差分は per-task 文字数バジェットの内側に収める。(2) **compact 110→112 は A-1 の承認範囲内**と判定し `human_recheck_required` へ昇格しない。根拠は、当該上限が「express template 上限 188 = requirements-template-express 76 + compact 112」という A-1 と同一の導出式の**従属変数**であり独立した裁量値ではないこと、112 を据え置くと 188 に到達できず A-1 が定義上成立しないこと、裁量パディングを含まないこと、T-26 の ratchet down 対象に含めたこと、の 4 点。(3) **T-26 に ratchet down 手順を追加**し、4 つの上限すべて（shell 2 ファイル × 3 箇所 + pytest 1 箇所 + 行末コメント）を対象にする。非 vacuous 確認（上限をさらに 1 下げると fail する）まで含める。(4) **AC-W0-1 の位置づけを変更**: 「既存 failure 2 面を解消する」は main 追従で失効し、純粋な bump（0.27.1 → 0.28.0）+ CHANGELOG + 4 拠点同期になる。D-5 / D-6 の機構は再発防止として維持する。
- **Why**: A-1 の承認文が「T-26 に ratchet down 手順を追加することが本決定の条件。上限が緩んだまま残すことは承認していない」と明記しているため、ratchet down は任意の後始末ではなく承認の一部である。compact 112 を人間に差し戻さない判断は、承認された数式の従属変数を機械的に解いた結果であって新しい裁量の行使ではないという点に依る（新しい裁量であれば AC-W2-7 の趣旨により差し戻すべきだった）。加えて、引き上げ後の残枠が **1 token / 0 行**しかないことを実測で確認したため、per-task 文字数バジェットを課さないと同じ差し戻しが 3 回目を迎える。「10 行以内」のような行数制約は文字数を縛らないため、行数と文字数の両方を task ごとに機械確認する形にした。

## ADR-W1-12: allow list の kind 種別を design の正本に登録し、類似度 0.8 の保証範囲を実測境界へ訂正する

## ADR-W1-14: 条件付き表示規範は「3 文セット」を単位として 2 正本に置き、記録先の受け皿と owner を同時に確定する

- **Context**: T-8 は無条件必須 3 件（`Workflow Fit Check` / `Adversarial Requirements Review` / `LLM 方針レビュー`）を条件付き表示へ置き換えたが、impl-gate 旧#1 が Medium 2 件を検出した。(F-1) design.md §5 の規範 3 文のうち**中間の「HITL には人間の判断が必要な場合だけ出す」だけが第 2 正本 `references/requirements-gating-steps.md` と第 1 正本の短縮形 2 箇所に入っておらず**、`Dialectic Review Lane=selected` かつ人間判断不要のケースで 2 正本が逆を指していた（AC-W2-2 の「両方で一致」未達）。(F-2) 新設した「`Workflow Fit Check` は判定結果と理由を requirements.md に必ず記録する」に対し `references/requirements-template.md` に受け皿が **0 件**で、owner task も無く、省略条件が AC-W2-2 / SKILL.md :240 / tasklist T-9 の planned コメントで三重に食い違い、`not_applicable` は当該欄の値域（3 値）に存在しない到達不能規範だった。

- **Consequences**: (1) 第 2 正本に `Workflow Fit Check` の bullet を新設し、3 欄すべてが 3 文セットを持つ状態にした。第 2 正本は express / standard いずれの runtime profile にも入らないため budget コストは 0。(2) 第 1 正本は per-task 文字数バジェット内に収めた（BC-2 実測。上限 25030 に対し残枠あり。行数 ±0、A-1 の 4 上限は不変）。:162 の「HITL 前に露出する」は同一文内で「〜場合だけ出す」と矛盾していたため削除した。(3) design.md §5 に WHERE 3 件（第 2 正本の中間文 / `references/requirements-template.md` の記録先と owner / 値域と省略条件）と A-19 の検査方針を追加。(4) tasklist T-9 に `references/requirements-template.md` を Files 追加し Step 2c を新設、Step 1 の assert を 3 語 × 2 正本 + 受け皿存在へ拡張、Step 2 の planned コメントを統一条件へ書き換え。(5) **A-17 の「なぜ GDD の重さを受け入れるかを承認ポイントに残す」義務は撤回せず第 2 正本へ移設**したため、AC-W2-7 の保護純減台帳への記録は不要。(6) AC の追加・削除・意味変更なし。統一後の省略条件は AC-W2-2 の `not_applicable` 条項を包含する。(7) 検証: 全 37 check 失敗 0 件 / full suite 872 passed・0 failed・1 skipped・650 subtests / (BC-1) exit=0 / `hooks/` 配下の変更 0 件。

## ADR-W1-24: 完了判定の検査語は「名指し」で置く。worker 自己選択型と分母を測っていない完全性主張を許さない

- **Date**: 2026-08-17 / **Status**: accepted / **Route**: design_detail_only（design-gating D11）
- **Context**: R4 は実レビュー advisory A-4 を受けて T-22 / T-23 の vacuous な Verification（`grep -c "<task> 検査結果" worklog.md >= 1` だけ）を位置拘束型へ差し替え、Self-Review 5b に「**PR-W1a の全 15 task** の Verification を走査し vacuous 型が 2 件残っていたので差し替えた」と完全性を主張した。本 gate の実測でこの主張が 3 点で崩れた。**(a) 分母が違う** — `PR Boundary: current-pr` の task は **18**（`awk` で機械集計）。「15」は tasklist:11 / :3396 / :3500 の 3 箇所に、対になる「移管した 12 task」は requirements:507 / adr:183 / state:159 の 3 箇所にあり、実測は **10**（tasklist 側は 10 と書いていて不一致）。**(b) 取りこぼしがあった** — **R4 が同じ commit で新設した T-24 Step 6** の Expected が `grep -c 'PR-W1a' <計画ファイル> >= 1` で、(i)〜(iv) の反映内容に一切触れず計画ファイルのどこかに `PR-W1a` を 1 回書けば緑になる。「更新前は 0 件」の事前実測は差分が生じたことしか示さず、どの内容が入ったかを位置で拘束していない。**(c) T-22 / T-23 の差し替えも被覆が足りない** — T-22 は名指しが 1 語（`初期案・壁打ちから変わったこと`）だけで、同じ対象ファイルに**現行テンプレートに 1 件も存在しない語**があと 4 語残っていた（`このOKでAIが自走した場合` / `このOKで承認するもの` / `人間が見るべき重要ポイント` / `OKだけではやらないこと`。5 語とも正本 2 本で `grep -c` = 0 を実測）。T-23 は「Step 1 でヒットした語のうち語彙が変わったものを検査語にする」という **worker 自己選択型**で名指しが 0 件だが、実際には機械検査可能な明確な誤りが実在した（`docs/DISTRIBUTION_READINESS.md:147 / :199 / :207` と `docs/NON_ENGINEER_APPROVER_HANDOUT.md:23` が `30秒判断` を lint の要求として案内するが、当該語は T-5 で `FINAL_HITL_REQUIRED_PHRASES` から削除済み）。
- **Decision**: **(1)** 件数の正本を機械導出コマンド（`awk` で `PR Boundary` を集計）とし、tasklist § PR Boundary Ledger に置く。文中の数値はすべて導出結果の再掲として扱い、15 → **18** / 12 → **10** を 6 箇所で訂正する。**(2)** Self-Review 5b を 18 task の分母で取り直し、未完了 9 task を全数走査した結果（vacuous 3 件 / 非 vacuous 6 件）を表で残す。**(3)** T-24 Step 6 の Expected を (i)〜(iv) 4 項目それぞれの検査語ペア（AND 判定 + 更新前値の事前実測）へ置換する。**(4)** T-22 Verification (i) を **5 語の位置拘束ペア**へ拡張し、「変更不要」分岐を削る。**(5)** T-23 Verification (i) を DISTRIBUTION_READINESS.md の 3 箇所と NON_ENGINEER_APPROVER_HANDOUT.md:23 を**名指し**した before/after ペアへ置換する。
- **Why**: (1) **分母を間違えた完全性主張はそれ自体が「記録が実態とずれる型」**（D-29）。同じ数値を 6 箇所に手書きしていたことが原因なので、正本を機械導出に一本化する。(2) **worker 自己選択型の検査語は「何も選ばなければ何も検査されない」** ので完了判定として成立しない。名指しがある箇所は名指しで縛る。(3) **T-22 / T-23 の被覆不足は承認根拠と矛盾する** — 承認ポイント B-2 が承認されたのは「実在しない旧見出しを案内する承認者向け手順書を出荷しない」という根拠を提示したからで、5 語中 1 語ぶんしか完了判定に反映されていない状態はその根拠を満たさない。(4) **「変更不要」分岐を残さない理由** — 5 語も `30秒判断` も**正本に実在しないことが実測済み**で、「実在しない見出しを案内し続けてよい」根拠は原理的に立たない。分岐を残すと worker が根拠を書かずに素通りする経路が開く。(5) **置換後側を対で拘束する理由** — 旧語を消すだけだと承認者向けの案内そのものが消え、「消しただけ」の状態が緑になる。かつ `docs/NON_ENGINEER_HITL_GUIDE.md` は置換後語彙の編集前実測が **2** なので、「1 以上」を条件にすると編集前から緑（= vacuous）。**編集前値からの純増**で判定する。
- **Consequences**: (1) tasklist § PR Boundary Ledger に機械導出コマンドと 2026-08-17 実測値（PR-W1a 18 / PR-W1b 10）を追加。`grep -c 'deferred-to-PR-W1b'` が 11 を返すのは説明文 1 行を含むためであることも明記。(2) tasklist:11 / :3396 / :3500 と requirements:507 / adr:183 / state:159 を訂正。(3) T-22 / T-23 / T-24 の Verification と各 task の `Verification:` メタ行を更新。(4) 各検査の**編集前実測値**（T-22: 2/1/1/2/2 と置換後側 GUIDE 2・team-onboarding 0 / T-23: DISTRIBUTION_READINESS 3・HANDOUT 1・TEAM_ROLLOUT 0 と置換後側 0/0 / T-27 A-3: PR-W5 0・0.0089 0・legacy anchors header incomplete 0・AllowList.load 1）を tasklist に記録し、非 vacuous を担保した。(5) **AC の追加・削除・意味変更なし**。Approved Direction・A-1 の 4 上限・承認ポイント B の 3 決定・hooks 配下はいずれも不変。(6) 新しい script / lint / 検査機構は追加しない（既存の `grep` / `awk` / `pytest` だけで閉じる）。
