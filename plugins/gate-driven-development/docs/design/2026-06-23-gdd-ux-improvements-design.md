# 設計文書: GDD UX 改善 — 停止・案内・中間報告の4カテゴリ対応

**日付**: 2026-06-23
**ステータス**: Draft
**対象バージョン**: gate-driven-development (local plugin)

---

## 背景・動機

5セッション調査で以下の4カテゴリの問題を確認した:

| カテゴリ | 内容 | 発生セッション数 |
|---------|------|---------------|
| A | 停止時「👤 次にすること」ブロックを hook に指摘されるまで書かない | 4件 |
| B | タスクスコープが変更されたとき未対応タスクを告知しない | 1件 |
| C | root-cause-investigation で中間報告がなく、完了後の次ステップ案内もない | 1件 |
| D | 長時間セッションで発見事項が記録されずコンテキスト枯渇で状態ロスト | 1件 |

---

## 設計ゴール

1. 停止時の「👤 次にすること」ブロックを Claude が **proactive に（hook なしで）** 出すようにする
2. スコープ変更時に未対応タスクを自発的に告知するルールを追加する
3. root-cause-investigation に中間報告チェックポイントと完了後の遷移案内を追加する
4. root-cause-investigation の発見事項をレジャーに記録し、コンテキスト枯渇から回復できるようにする

## 変更詳細

### 変更1: output-format.md — カテゴリA（proactivity 注記）

「停止時の 👤 次にすること マップ」テーブルの**直前**に以下の注記を追加する（実装時に `grep -n "次にすること マップ\|👤" output-format.md` で正確な anchor を確認すること）:

```markdown
> **MUST: proactive に書くこと**
> このブロックは stop hook が出力後に検査するが、**hook に頼らず最初から書くこと**。
> hook に指摘されてから追加するのは reactive 修正であり、不要なコンテキストを消費するため禁止。
> subagent をバックグラウンド起動して停止する場面でも必ず書く。
```

---

### 変更2: output-format.md — カテゴリB（スコープ変更通知ルール）

停止構造セクションの末尾（または `## 停止構造` セクションの最後の項）に以下を追加する:

```markdown
### スコープ変更通知

セッション中にタスクの対象・範囲が変わった場合（別サブタスクへの移行・問題の切り分け・意図的な絞り込みを含む）、
以下を停止出力または作業完了報告の末尾に **必ず** 追加する:

> **スコープ外になった項目**
> - <元のタスクや要求で、今回対応しなかった項目>
> - 理由: <スコープ外にした理由>
> - 対処が必要な場合: <ユーザーが次にすべき操作>

スコープ変更に気づかず省略した場合、ユーザーは「対応済みか未対応か」を判断できない。
```

### 変更3: root-cause-investigation/SKILL.md — カテゴリC（中間報告・サイクル・遷移案内）

SKILL.md の調査プロセス定義の末尾に以下のセクションを追加する:

```markdown
### 中間報告ルール（10ツール呼び出しごと）

10ツール呼び出しごとに、以下の形式で中間サマリーを **ユーザーに向けて** テキスト出力する:

> **調査中間報告**（ツール呼び出し N 回目）
> - 確認済みの事実: <箇条書き>
> - 現在の仮説: <1-2行>
> - 次に検証すること: <1-2行>
> - 残り不明な点: <箇条書き>

### 仮説→検証→結論サイクルの遵守

調査は以下のサイクルで進める。サイクルを飛ばして深掘りしない:

1. **仮説を立てる**: 証拠から根本原因の候補を1-3個絞る
2. **検証する**: 仮説を確認/反証できる最小のツール呼び出しを行う
3. **結論を更新する**: 証拠が仮説を支持するか判断し、次の仮説に移る
4. **収束判定**: 仮説が1つに絞られ、確認証拠が揃ったら調査完了

### 調査完了後の遷移案内

調査が完了したら（`<gdd-stop reason="done">` 出力時）、`👤 次にすること` に以下を含める:

- 根本原因のサマリー（1-3行）
- 修正が必要な場合: 「修正を進めるには『修正して』と指示してください」
- GDD フローで進める場合: 「`/gdd-dev` で修正フェーズを開始できます」
```

### 変更4: root-cause-investigation/SKILL.md — カテゴリD（レジャー記録ルール）

SKILL.md のプロセス定義に以下の永続化ルールを追加する（変更3と同ファイル・同セクション付近）:

~~~~markdown
### 調査発見事項のレジャー記録

重要な発見（根本原因の特定・確認証拠・除外した仮説）は都度、以下のファイルに記録する:

ファイル: `.gdd/rci-findings.md`（なければ作成）

```markdown
# Root Cause Investigation Findings

## <タスク名> (<日付>)
- **確認済み**: <発見事項>
- **除外**: <除外した仮説と理由>
- **現在の仮説**: <最新の仮説>
```

このファイルはコンテキストが切れても残るため、再開時に Read することで調査状態を復元できる。
長時間調査（ツール呼び出し 20回超）では必ず記録すること。
~~~~

## 防御層の全体像

```
カテゴリA: output-format.md の proactivity 注記
  → 「hook に頼らず最初から書く」を明示 → reactive 修正サイクルをなくす

カテゴリB: output-format.md のスコープ変更通知ルール
  → スコープ変更時に必ず未対応項目を告知する

カテゴリC: root-cause-investigation の中間報告 + サイクル + 遷移案内
  → 調査の可視性向上 + 完了後の次ステップ明確化

カテゴリD: root-cause-investigation のレジャー記録
  → コンテキスト枯渇後も調査状態を復元可能に
```
