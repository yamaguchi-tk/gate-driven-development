## ADR-1: `human-check-template.md` はアーカイブ移動せず蒸留する（Option D 却下）

- **Context**: 設計書 Task 1 は「ロード実績が無い reference は蒸留せずアーカイブへ移動（そちらが優先・低コスト）」という分岐を持ち、requirements は `references/human-check-template.md`（773 行）をその候補として Option D に切り出し、判定を design-gating へ委譲していた（human check 承認ポイント 4）。
- **Decision**: Option D を採らず、他 3 references と同じ 5 ステップで蒸留する。
- **Why**:
  1. 分岐条件が成立しない。`skills/gdd-requirements-gating/SKILL.md:281` が「human check 停止時は `references/human-check-template.md` を Read し、テンプレートをそのまま埋めて出力」と定めており、標準経路の必読正本である。requirements が根拠にした `gdd-brainstorming/SKILL.md:267`（full 版は必要時だけ参照）は「HITL 本文に長い表を貼るな」という表示規律であって、ロードしないという意味ではない。
  2. path 変更は delivery path の変更であり、`references/rollback-patterns.md` § design_detail_only の除外条件に触れる。低コスト分岐という前提が崩れ、`human_recheck_required` を要する変更になる。
  3. 移動しても references 合計行数から 773 行が消えるだけで実行時ロード量は減らない。この値を分母に S-3 のラチェットを打つと、以後の references 予算が虚偽の基準になる（AC-11 と § Verification Sanity Check が塞ごうとしている罠と同型）。
  4. 非 archive の参照が 30 ファイル超（契約テスト 15 / `evals/` / `tests/checks/` の 2 lint 表 / `required_files` / `commands/gdd-dev.md` / `references/` 内 5 箇所）あり、一括更新のコストとリスクが蒸留を上回る。
- **Consequences**: 蒸留対象は 8 件のまま（Approved Direction どおり）。`human-check-template.md` は契約テスト被参照が最多（15 本）なので、S-1 の 3 番目（手順が安定した後）に置く。requirements § Option D の背景記述にあった「通常経路では compact 版だけが読まれる」という認識は誤りとして design 側で訂正済み。AC の追加・削除・意味変更はない。

## ADR-2: アンカー逆引き（AC-1 集合 (3)）は base commit のツリーに対して実行する

- **Context**: Option B は 8 対象を順に蒸留する。集合 (3) は「テスト側から原本へ逆引きした被参照文字列」であり、走査対象に `references/` と `skills/` が含まれる。対象ごとに作業ツリーを走査すると、先に蒸留した対象から文字列が消えて後続対象の分母が縮む（fail-open）。
- **Decision**: (3) の逆引きは常に base commit `33cb8aa5` を展開した pristine tree に対して実行し、走査対象から原本自身と `docs/references-archive/**` を除外する。
- **Why**: 分母を処理順序から独立させることで、AC-1 の「事後の分母差し替え禁止」がより強く成立する。順序を「安全性」ではなく「効率」で決められるようになり、8 対象の並べ替えが自由になる。原本自身と旧 archive を除外しないと自己一致・旧コピー一致で分母がノイズだらけになる。
- **Consequences**: `docs/audits/r9-2-anchor-tools.sh extract` は base tree の展開先を引数に取る。分母は base 固定なので、蒸留が進んでも各対象の anchors.txt は再現可能（AC-1 の再実行性を満たす）。

## ADR-3: アンカー照合は `docs/audits/r9-2-anchor-tools.sh` として実装する（`scripts/` に置かない）

- **Context**: requirements § 非採用案は「新規 Python スクリプトを `scripts/` に追加する」案に対し、保守面が増えるとして design-gating での判断を求めていた。AC-1 は「再実行可能な手順」しか要求しない。
- **Decision**: `extract` / `verify` の 2 サブコマンドを持つ単一シェルスクリプトを `docs/audits/` に置き、最初の archive コミットに含める。抽出コマンド列は監査シートにも逐語で残す。
- **Why**: `scripts/` は配布物の runtime 保守面で、`lint-scripts-syntax.sh` / `lint-scripts-functional.sh` の明示 allowlist への登録可否という判断が増える。本ツールは Wave 1 限定の作業用であり、Wave 完了後に削除できる位置が正しい。`docs/audits/` は `docs-links-valid.sh`（`docs/*.md` の非再帰 glob）の走査対象外で、既存 check を 1 つも増やさない。
- **Consequences**: 8 対象 × 5 集合の照合が手作業の grep 列ではなくスクリプトで再現できる。RED 先行（アンカー 1 件を削ったコピーで `verify` が exit≠0）を各対象で確認してから本番適用する。却下案: 監査シート内のコマンド列のみ（8 対象 × 5 集合では転記ミスの確率が高い）。

## ADR-4: AC-11 を `git diff --numstat` ベースの機械判定に落とす

- **Context**: AC-11（`削除行数 ≧ 移送行数`）は Option A 前提で `gdd-brainstorming` の移送に課した割引条件だった。Option B では移送が最大 4 スキルで発生する。
- **Decision**: 適用対象を「実行時にロードされうる場所（`references/*.md` または他 `SKILL.md`）への移送を含む全対象」とし、判定を `移送行数 = references/*.md の純増行数` / `削除行数 = skill body 減少行数 − 移送行数` と定義して、`skill body 減少行数 ≧ 2 × references 純増行数` で機械判定する。`docs/` への移送は、蒸留後本文に `docs/...` へのポインタを残さない場合のみ「削除」に計上する。
- **Why**: 「移送か削除か」を人間の読解に委ねると対象ごとに判定がぶれる。コミット単位の numstat なら監査シートの行数内訳と一致し、事後検証もできる。ポインタが残る `docs/` 移送は実行時に読まれうるので削除として数えられない。
- **Consequences**: AC-11 は Option B でも意味を保つ。不成立の対象は「移送のみで実質削減なし」と監査シートに明記し、S-3 の引き下げ根拠の説明から外す（バジェット引き上げは行わない）。判定式の RED 確認（削除 0・移送のみの diff で不成立になること）を 1 度実施する。

## ADR-5: `--max-skill-body-lines` も承認済みの余裕率規則をそのまま適用する（+5% 時点は 365 → **Amendment 1 により +2% / 予測値 354**）

- **Context**: 承認ポイント 3 で引き下げ幅は「蒸留後実測 + 5%」と決まった。Option B では蒸留 4 スキルが全て 350 body 行以下になり、`--max-skill-body-lines`（全 28 skills に適用）の下限を決めるのは蒸留対象外の最大 skill = `gdd-completion-check`（347 行実測）に変わる。当初案は「`skill-body-budget.sh` のハードキャップ 350 に合わせて 350 を採る」だったが、design review（M5）で AC-6 の文言（7 値すべてが「実測 + 承認された余裕率」と一致）からの逸脱であり、completion-check で AC-6 未達と判定される余地が残ると指摘された。
- **Decision**: 当初案を撤回し、`ceil(347 × 1.05) = 365` を採用する（蒸留後に 348〜350 の skill が出たらその実測で再計算）。7 値すべてが同一規則で決まる。
- **Why**: 承認ポイント 3 で人間が承認したのは「実測 +5%」という規則そのもの。1 値だけ別規則を採るのは承認内容からの逸脱にあたり、`design_detail_only` の範囲（境界値の変更は human_recheck 対象）を外れる。365 は `skill-body-budget.sh` の `MAX_SKILL_BODY_LINES=350` より緩いので冗長な backstop になるが、**厳しい側（350）が常に先に落ちる**ため判定は一意で、実害はない。承認済み規則を design 側で書き換えないことを優先する。
- **Consequences**: 実効的に binding なのは 350 のまま。`gdd-completion-check`（347）/ `gdd-using-git-worktrees`（343）の headroom が 3 行 / 7 行になる点は変わらないので、S-3 時点で 350 を超えていないことを実測確認する。超えていた場合は蒸留対象を勝手に追加せず human check へ戻す（Approved Direction の scope 外）。
- **Amendment 1（`hc-20260731-5`: 余裕率 +5% → +2%）**: 決定の**構造は不変**（承認された余裕率をそのまま 1 値だけ例外なく適用する / binding は `skill-body-budget.sh` の 350 / 厳しい側が先に落ちるので判定は一意）。**値のみ `ceil(347 × 1.05) = 365` → `ceil(347 × 1.02) = 354` に変わる**（ただし **354 は T-6 / T-7 / T-8 が 3 本とも ≤350 に到達した場合の予測値**。`--max-skill-body-lines` は全 28 skills に適用されるため、T-6 だけ ≤350 で T-7 / T-8 が未達なら制約元は `gdd-writing-skills`（590）で `ceil(590 × 1.02) = 602` になる。実際の新値は T-10 の一括実測で決まり、design が固定するのは算出規則だけ。**T-10 で 354 をハードコードしないこと**）。ADR-11 で余裕率そのものが改定されたことによる従属変更で、この ADR の判断内容を覆すものではない。あわせて 旧#7 の充足条件を実測から明示する: AC-6 旧#7 は「全 28 skills の最大 body 行 ≤ **636**」で成立する（`ceil(636 × 1.02) = 649 < 650`、637 では 650 で不成立）。制約元は現時点で `root-cause-investigation`（644 行、T-6 未着手）なので、**T-6 で 8 行削るだけで 旧#7 は成立**し、AC-8（≤350）はその上位互換。T-7 / T-8 の対象（590 / 484）はいずれも 636 以下のため 旧#7 の成否には影響しない。詳細は `design.md` D-5 Amendment 2。

## ADR-8: AC-6 の「現行値より小さい」を満たすため、profile 収載 2 ファイルにトークン基準の削減目標を課す（**Amendment 1 により失効**）

- **Context**: design review（H1）で、AC-6 が「現行値より小さい」と「蒸留後実測 × 1.05 と一致」の**両方**を課すことが検算された。両立には `蒸留後実測 ≦ floor((現行値 − 1) / 1.05)` が必要で、express 推定トークンは **−1,522**、standard 推定トークンは **−2,712** の削減が要る。ところが design の当初目標は `gdd-brainstorming` が「350 body 行以下」（現 352 行 → −2 行 ≒ −50 トークン）で、30 倍の乖離があった。express profile 9 ファイルのうち 8 対象に含まれるのは `gdd-brainstorming` 1 本だけなので、この 1 本が全額を負担する。
- **Decision**: 行数目標ではなくトークン目標を正本にする。`skills/gdd-brainstorming/SKILL.md` ≤ 7,163 トークン（−17.5%、概ね 290 body 行）、`references/requirements-template.md` は standard 側で追加 −1,190 トークン かつ 702 行以下（standard template 上限 旧#4 の要件）。「350 body 行以下」はバジェット例外リスト解消（AC-8）の最低条件として残すが、AC-6 の達成条件ではないと design に明記する。
- **Why**: この乖離を S-3（全 8 対象の蒸留完了後）まで持ち越すと、そこで初めて「規則どおり引き下げると現行値を上回る」と判明し、(a) AC-6 を破る (b) 承認済みの +5% を破る (c) scope 外の追加蒸留 のいずれかを迫られる。どれも human check への出戻りで、8 対象の作業を終えた後では手戻りが最大化する。設計段階で必要削減量を各ファイルに割り付けておけば、蒸留 subagent への指示に最初から織り込める。
- **Consequences**: `gdd-brainstorming` の難度が上がる（free 行 204 行のうち約 3 割を削る）。AC-11 により移送では稼げないため実質は削除主体になる。実現可能性は実測で確認済み（AC-1 の 5 集合でロックされない free 行は `gdd-brainstorming` 204 行 / `requirements-template.md` 223 行で、必要削減量は範囲内）。達成できない場合はバジェット据え置き・余裕率の縮小・scope 外の追加蒸留のいずれも行わず、AC-6 未達を記録して human check へ戻す。
- **Amendment 1（`hc-20260731-5`: 余裕率 +5% → +2%）— per-target のトークン目標を失効させる**:
  - **判断**: ADR-11 で余裕率が +2% になった結果、AC-6 旧#5 / 旧#6 は **per-target の割り付けなしに現時点の実測で成立する**（express 実測 32,778 ≤ 必要上限 32,940 / standard 実測 55,978 ≤ 必要上限 56,469）。したがって本 ADR が割り付けた `requirements-template.md` の追加 −1,190 トークン と `gdd-brainstorming` ≤7,163 トークンは**役目を終えたものとして失効**させる。条件付きで残すことはしない（残すと、AC でない目標の未達が AC 違反と誤読され、T-5 / T-9 で実際に起きたのと同じ差し戻し判断を再発させる）。
  - **失効させる範囲はトークン目標だけ**。`requirements-template.md ≤702 行`（AC-6 旧#4 = standard template 上限に直接効く）と `350 body 行以下`（AC-8）は AC 由来の条件なので存続する。いずれも達成済み（693 行 / 312 行）。
  - **未達判定の取り消し**: T-5 の −847 トークン（目標 −1,190 に −343 不足）と T-9 の 7,942 トークン（目標 ≤7,163、RED 再測 ≤6,820 に未達）は、**+2% 下では AC-6 違反ではない**。本 ADR の per-target 割り付けに対する未達であり、AC への未達ではない。実測値は監査シート / CHANGELOG に記録したまま残し、AC-6 の最終判定は T-10 の 7 値実測で行う。
  - **本 ADR の Decision 自体は誤りではない**: +5% を前提とした当時、per-target 目標がなければ S-3 で初めて破綻が判明する構造だった。実際に破綻したのは目標値ではなく「約 −60% 削減できる」という上流の前提で、それが実測（約 −4%）で覆ったため余裕率側を動かす選択になった。設計段階で必要削減量を逆算しておいたこと自体が、S-3 到達前にこの矛盾を検出できた理由でもある。
  - **T-6 / T-7 / T-8 にトークン目標は課さない**: 3 対象は express / standard profile 非収載で AC-6 旧#5 / 旧#6 に非寄与。残る責務は AC-8（≤350 行）/ AC-6 旧#7 の制約元移動 / skill body 合計の引き下げの 3 点のみ。移送先が standard profile 収載 references の場合だけ headroom を確認する（`design.md` D-5 Amendment 2 の guardrail）。

## ADR-9: アンカー抽出パターンを実データで確定する（`〜しない` はプレースホルダ）

- **Context**: design review（H2 / H3）で、AC-1 の抽出パターンをそのまま実装すると分母が黙って縮む経路が 2 つ見つかった。① requirements の `〜しない` はリテラルとしては 4 references に **0 件**しかマッチせず（実際は `しない` が 30〜71 件）、否定形の規範文が丸ごと保護対象から落ちる。② 集合 (3) の「文字列リテラル」が markdown 側で未定義で、走査対象に `commands/` が入っていない（D-1 の判定根拠 `commands/gdd-dev.md:185` が分母外だった）。
- **Decision**: 規範表現パターンを `してはならない|禁止|必ず|fail-closed|しない|しないこと|するな` に確定。集合 (3) の走査対象に `commands/**` と `agents/**` を追加し、markdown の抽出規則を「インラインコード span + 見出しテキスト、8 文字以上」と定義する。`anchors.txt` の先頭に集合別の抽出件数を記録し、0 件の集合が出たら fail-closed とする。
- **Why**: どちらも **under-extraction** で、D-A の RED 確認（アンカー 1 件を削って verify が fail するか）は照合器の健全性しか見ないため検出できない。requirements § Verification Sanity Check が自ら警告している「20/20 一致でも 180 件見落としていれば 100% と報告できる」穴そのもの。件数の記録と目視サニティチェックが唯一の防波堤になる。
- **Amendment（design review 2 巡目 N1 / N2）**: ① 「0 件なら fail-closed」は実データで誤発火する（`state-machine.md` はコードフェンス 0 件、`human-check-template.md` と `gdd-writing-skills` は `Step <数字>` 0 件。しかも `state-machine.md` は処理順の初手）。`extract` 時に「空であることが正当な集合」を anchors.txt ヘッダへ事前記録して archive と同じコミットに固定し、記録の無い 0 件だけを故障扱いにする。② ノイズ対策の「8 文字以上」フィルタが、契約テストが実際に grep している日本語語彙（`承認ポイント数` / `人間に戻す条件` / `停止理由` 等）を分母から 38〜45% 落とすことが実測で判明したため、**ASCII は 8 文字以上 / CJK を含む文字列は 3 文字以上**に変更した。
- **Consequences**: 分母は AC-1 の記述より**広がる**方向（保護が強くなる）ため AC の意味変更にはあたらない。ロックされる行が増えるぶん蒸留の自由度は下がる（実測: `human-check-template.md` は 773 行中 512 行がロックされ free は 22%）。この制約は ADR-8 の削減目標と両立することを実測で確認済み（削減目標が課される 2 ファイルの free 行は 57% / 31%）。

## ADR-6: AC-3 は P1 subagent lane ではなくアドホック 2 ファイル dispatch で実施する

- **Context**: requirements は AC-3 の実施手段について (i) `run-gdd-scenario-evals.py --emit-subagent-prompts` の P1 lane を第一候補とし、採らない場合は理由を記録するよう求めていた。
- **Decision**: (ii) archive 原本と蒸留版の 2 ファイルパスだけを新規 subagent に渡す方式を採用する。P1 lane は本 Wave の gate にも証跡にも使わない。
- **Why**: `write_subagent_prompts` / `render_subagent_prompt` を実読した結果、P1 lane が生成するのは fixture の 53 シナリオそれぞれについて「GDD ワークフローを実行させる評価 prompt」であり、原本と蒸留版を突き合わせる機能を持たない。前後比較の成立には蒸留前後で artifact を再生成する必要があるが、入力 artifact は 2 件しかなく拡充は非スコープ。測れるのは「蒸留後 skill が書いた成果物が checklist を満たすか」であって、AC-3 が求める逐語の欠落・捏造検出ではない。
- **Consequences**: requirements § 非採用案の「P1 lane が使えないと design-gating で判明した場合のフォールバック」条件に合致する形で (ii) を採用。AC-3 は引き続き `external-evidence-required`（決定論でない）で、Honest Limitations と CHANGELOG への明記（CT-3）で補う。

## ADR-7: 蒸留はメインではなく対象ごとの subagent が行い、メインは原本を Read しない

- **Context**: Wave 0 の事故は、コンテキスト圧縮下でメインが原本を部分読みしたまま記憶で再構成し、Step 8a〜8h の意味取り違えなど 7 種類の捏造を生んだこと。Option B は対象が 4 倍でリスクが比例して上がる。ユーザーは「Opus 5 なら行ける」と述べたが、モデル強化は原本滞留の問題を解かない。
- **Decision**: ①archive コミット ②アンカー抽出 ④照合 ⑤テスト ⑦コミット をメイン（Bash 中心・原本 Read 禁止）、③監査シート作成 + 蒸留 と ⑥逐語照合 を**それぞれ別の新規 subagent（Opus 5）**に委譲する。蒸留 subagent は成果物を直接 Write し、戻り値は 20 行以内のサマリに限る。
- **Why**: 原本全文がメインのコンテキストに載らなければ、圧縮による部分読み → 記憶再構成という事故経路自体が発生しない。③ と ⑥ を同一インスタンスにすると「自分の書いたものを自分で検証する」ことになり AC-3 の独立性が消える。
- **Consequences**: メインが原本の中身を必要と感じたら、それは subagent への指示不足であり、Read せずに指示を作り直す（fail-closed）。対象間で subagent を使い回さない。同一対象で照合指摘が 3 回目なら human check へ戻す。
- **Amendment（design review M1 / H4 を受けて）**: 工程分離だけだと、監査シートが「削った本人の自己申告」になり誰も原本と突き合わせない構造が残る（AC-1 が守れない領域の唯一の補償統制がこれ）。⑥ の入力に **③ が書いた監査シートを追加**し、「節別判定の申告と実際の蒸留結果が食い違っていないか」を検証項目に含める。⑥ には独立性を保ったまま検証材料を渡す形になる。あわせて、2 ファイルだけ渡された照合者が「承認された削除」と「欠落」を区別できず全件指摘か全件素通しのどちらかに壊れる問題に対し、⑥ の prompt 契約（前提・指摘条件 6 種・出力スキーマ・禁止事項）を `design.md` § D-3 に固定した。

## ADR-10: アンカーツールを Python 単一実装へ書き直し、`extract` と `verify` に同一パーサを共有させる

- **Context**: `docs/audits/r9-2-anchor-tools.sh` は AC-1 の証跡そのものだが、**3 巡連続で同じ型の fail-open** が出た。巡 1（T-2 impl-gate）= anchors 不在でも exit 0 / 非アトミック書き込みの残骸を 0 件照合で pass / `## SET ` 前方一致の衝突。巡 2（T-3 逐語照合 F-1）= フェンス判定 `/^```/` の行頭限定で 50 行が分母外、同型が他 3 箇所。巡 3（T-3 impl-gate F-2）= 巡 2 の修正で足した `--allow-missing` に同型。照合は `grep -qxF`、宣言カウントは `grep -cvE '^[[:space:]]*(#|$)'` と**同じファイルを別ルールで読む**ため `#` 始まりの見出しアンカー 44 件が「例外として効くがカウントされない」。未承認の見出し削除が `ANCHOR_VERIFY_OK (3 allowed)` / exit 0 で通ることを本番 anchors 597 件で実測した。根本原因は `extract` と `verify` が同じテキストをそれぞれ別の ad-hoc な grep / awk ルールで読んでいること。ルールを足すたびに読み方のズレが生まれ、ズレは常に fail-open 側に倒れる（照合されない行は「欠落なし」に見える）。同型は本プロジェクトの他所でも再発している（PreCompact hook の `sed` 行頭限定 / plan-reread hook の `### Task:` 厳密一致 / gate 判定の delimiter）。
- **Decision**: bash を捨てて **`docs/audits/r9-2-anchor-tools.py`（単一ファイル / 標準ライブラリのみ / サブコマンド `extract` `verify` `compare` `selftest`）** に書き直す。(1) 集合定義は `SETS` registry 1 つ、`extract` だけが writer で `verify` はアンカーを再導出しない。(2) manifest の I/O は dataclass + `json` のみとし、**内容行と衝突しうる区切り記法（`## SET N` / 行頭 `#`）を廃止**する。(3) 「アンカーが存在する」は述語 1 つ。(4) allow list は**パース済みリスト 1 本**から `declared` と `used` を派生させ、突合は集合等価。(5) `verify()` は `VerifyOk | VerifyFailed` しか返さず、`VerifyOk` は 7 条件（**Amendment で 9 条件へ拡張**）（schema 一致 / `total > 0` / candidate 非空 / verdict 数 == total / 集合別件数一致 / missing 0 / allow 集合一致）を通過した 1 箇所でしか構築できない。CLI は `except BaseException` で exit 2。ファイル名（`r9-2-<name>-anchors.txt` / `-allowed-missing.txt`）は据え置き、中身だけ JSON 化する。
- **Why**: 「同じ定数を 2 箇所に書かない」ではなく「**1 箇所しか定義できない**」形にしないと、3 巡すべてが示すとおり修正のたびに新しい読み方のズレが混入する。区切り記法の廃止は巡 1 の Medium と巡 3 の High を**バグクラスごと**消す（JSON のエスケープは全域なのでマーカー衝突・コメント誤認が原理的に起きない）。allow list を 1 オブジェクトから派生させると `used ⊆ declared` が構造的に成立し、F-2 の非対称は表現自体が不可能になる。型で「検査が走らなかった」と「検査が走って 0 件だった」を分けるのは、この 2 つを区別できないことが 3 巡すべての共通形だったため。ファイル名を変えないのは、requirements § Completion Testability Matrix が AC-1 の evidence としてこの名前を挙げており、**requirements 無改訂で閉じる**ため。python3 は既存 baseline（`scripts/lint-runtime-budget.py` / pytest 62 ファイル）に含まれ新規 runtime ではない。
- **Consequences**:
  - **配置は `docs/audits/` のまま**。`tests/*.py` は承認済み § 影響範囲 glob の外（Approved Direction の scope 外変更に該当）、かつ pytest が自動収集して Wave 1 限定ツールが恒久 release gate になるため移さない。`tests/checks/` + `manifest.tsv` も同じ理由で不採用。回帰 fixture も同じ判断で `selftest` サブコマンドに内蔵する（R1〜R18。3 巡の既知 fail-open + 対照 + design review で追加した extract 側ガード・重複アンカー・CLI exit code・旧形式リーダ・base tree 取り違えの各ケース）。各対象の `extract` 前に `selftest` を走らせ、出力を監査シートへ逐語記録する（fail したら蒸留に進まない）。
  - **既存 artifact との互換は superset で機械保証する**。T-2（686 件）/ T-3（597 件）を base commit `33cb8aa5` から再抽出し、`compare --old <旧 anchors.txt> --new <新 manifest>` で **旧集合 ⊆ 新集合**を検査する。満たさなければ fail-closed で human check。旧形式リーダは `compare` の中だけに閉じ、規則を design に逐語固定し、旧ヘッダの宣言件数（686 = 39+2+535+0+110 / 597 = 44+3+380+83+87）との突合を必須条件にする（リーダ自身の過少読みが superset 判定を spurious pass させるのを防ぐ）。**既存 `.txt` は凍結し上書きしない**（AC-1 の括弧書き「後から分母を差し替えられないようにする」を literal に満たすため）。再抽出結果は `-v2.txt` として別名で追加し、監査シートに (旧 blob sha, 旧件数, 新件数, compare 出力) を記録する。T-4〜T-9 は当初どおり `r9-2-<name>-anchors.txt` を archive コミットに含める。F-2 の実測 2 ケースも新ツールで exit 1 になることを確認する。
  - **`tasklist.md` の `Actual code` 逐語コピー（旧 bash 226 行）は廃止**する。同一ロジックの 2 箇所コピーは、いま直している欠陥と同型。代わりに (a) 実行コマンド行の逐語、(b) 実行時点のツール blob sha（T-2 / T-3 分は**削除前の旧 `.sh` の blob sha = `f449a84` 時点**を記録する）、(c) パスへのポインタを残す。T-2 / T-3 の監査シートに残る `.sh` 前提の抽出コマンド列も `.py` invocation へ差し替える（実行不能なコマンド列は AC-1 の「再実行して同じ分母が再現することを確認する」を満たさない）。T-4〜T-9 の Steps も新 invocation へ更新が要るため、design 承認後は `gdd-task-breakdown` へ戻す。

  - AC-1〜AC-11 は不変。抽出集合の定義・走査対象・フィルタ（ADR-9 / D-B）も不変。動くのは実装形態と証跡ファイルの内部形式のみ。
  - **Amendment（design gate `gdd-planning-reviewer` 1 往復 / High 3・Medium 5 をすべて反映）**: ① manifest の自己整合性 7 条件だけでは **wrong base tree からの extract が exit 0 で通る**（分母が縮んだまま counts / total は整合する）。archive 原本が base blob とバイト同一であること（`bce47f53...` / `9271992...`）を実測で確認し、`source_sha256` の突合を extract / verify 双方の必須条件に格上げ、`base_tree`（絶対パス）を `base_commit` へ置換。② `compare` の旧形式リーダが唯一残る ad-hoc パーサだったため、規則の逐語固定 + 旧ヘッダ件数との突合を必須化。③ 同名上書きを取りやめ、既存 `.txt` 凍結 + `-v2.txt` 追加へ変更（AC-1 文面との抵触を回避し human check を不要にした）。④ verdict のキーを `(set_id, anchor)` と明記（実データにクロス集合重複が 686 中 2 件 / 597 中 8 件あり、文字列キーだと恒久 false RED になり「その場でルールを緩める」経路を誘発する）。⑤ `present()` を「部分一致・正規化なし・大小文字区別」と逐語固定し、allow 判定を M3 の対象から外した。⑥ `main()` の戻り値を `isinstance(int)` で assert（`sys.exit(None)` = exit 0 の穴）。⑦ extract 側ガード（`expect_empty`）の回帰 fixture R13 / R14 を追加。⑧ design 本文の旧 `.sh` 前提記述（残る判断点 / D-3 工程表 / Architecture Recommendation Gate / Codebase Health Survey / WHERE / テスト方針 / fail-closed 条件）をすべて同期。**2 往復目**で新規 Medium 2 件（NM-1 = 条件 8 の archive パス導出が references 命名しかカバーせず、残り 6 対象中 4 本の `skills/<x>/SKILL.md` で規則未定義 → `TARGETS` registry を 8 行の表として design に固定し、archive 不在は skip せず exit≠0 / NM-2 = T-2・T-3 の以後の verify にどちらの manifest を使うか未指定 → `-v2` を正、凍結 `.txt` は `compare --old` 専用と明記）も反映。棄却 0 件。

## ADR-11: バジェット引き下げの余裕率を +5% → +2% に改定する

- **Context**: 承認ポイント 3 で「新値 = 蒸留後実測 + 5%」が承認された。そのときの根拠は「絶対値は下がりつつ運用余裕は増える」で、設計書の前提「約 5,000 行 → 約 2,000 行（−60%）」に依存していた。references 4 本（T-2〜T-5）と `gdd-brainstorming`（T-9）の実測で、実際の削減は **約 −4%**（references 合計 12,280 → 12,183 ほか）と確定し、前提が誤りだったことが判明した。削減量が想定の 1/8 だったため、+5% を適用すると **7 値中 4 値**（`--max-total-skill-body-lines` 7,536 / `--max-express-estimated-tokens` 34,417 / `--max-standard-estimated-tokens` 58,777 / `--max-skill-body-lines` 677）が現行上限を**上回り**、AC-6 の「現行値より小さい」を満たせない。
- **Decision**: 余裕率を **+2%** に改定する（`新値 = ceil(蒸留後実測 × 1.02)`）。`Human Check Status=approved` / evidence `hc-20260731-5` で承認済み。7 値すべてに例外なく同一規則を適用する点は変えない。
- **Why**:
  1. **AC-6 の文面はパラメータ化されている**。「蒸留後実測値 + **承認された余裕率**」であり、5% は AC ではなく承認ポイント 3 の決定値。よって AC-1〜AC-11 の改訂ではなく `design_detail_only`。
  2. **+2% ならラチェットと運用余裕が両立する**。7 値中 6 値が現行上限を下回り（残る `--max-skill-body-lines` も T-6 で制約元が移れば下がる）、同時に standard profile の運用余裕が 0.06%（57,568 / 57,600）から 2% へ回復する。承認ポイント 3 が本来求めていた性質を、正しい実測の上で再現する選択になる。
  3. **代替案はいずれも劣る**。(a) +5% のままバジェットを据え置く → ラチェットが効かず本 Wave の目的（S-3）が消える。(b) scope 外のファイルを追加蒸留して +5% でも下がるようにする → Approved Direction の scope 外で、8 対象の作業後に対象を増やす最悪の手戻り。(c) 値ごとに余裕率を変える → ADR-5 で「1 値だけ別規則を採らない」と決めた判断と矛盾する。
- **Consequences**:
  - `design.md` D-5 は **Amendment 2** が正本になる。元の +5% 前提の表・必要削減量表・旧#7 の下限決定は記録として残す。
  - **ADR-5 は予測値のみ 365 → 354**（Amendment 1）。354 は T-6 / T-7 / T-8 が 3 本とも ≤350 に到達した場合の予測値で、確定値ではない（実際の新値は T-10 の一括実測）。判断の構造（承認された余裕率を例外なく適用 / binding は 350）は不変。
  - **ADR-8 の per-target トークン目標は失効**（Amendment 1）。T-5 の −847 / T-9 の 7,942 は AC-6 違反ではなくなる。
  - **T-10 の実装に効く変更**: `bump()` の係数を `1.05` → `1.02` にする。`new < old` の assert（fail-closed）はそのまま機能し、`--max-skill-body-lines` だけは T-6 完了前に走らせると assert で停止する（意図どおり）。`tasklist.md` の T-10 `Actual code`・T-9 判定手順（≤6,820）・ヘッダ Human Recheck Boundary も同期が要る → `gdd-task-breakdown` へ回す。
  - **引き下げ後の運用余裕は 4〜244 行**（headroom = `新値 − 実測`。判定が厳密な `>` のため上限と同値までは pass する）。最も厳しいのは `--max-express-template-lines`（186 に対し実測 182 = 4 行）。「1 行足すと落ちる」状態ではないが、express テンプレート 2 本を将来拡張するときは上限の見直しを human check にかけることになる（`design.md` D-5 Amendment 2 の honest limitation）。
  - **移送時に binding するのは別の数字**: T-6 / T-7 / T-8 の移送は T-10 の引き下げより前なので、効くのは「引き下げ前の AC-6 余地」= `floor((現行上限 − 1) ÷ 1.02) − 実測`（旧#5 = 162 トークン / 旧#6 = 491 トークン / 旧#3 = 13 行 / 旧#4 = 33 行 / 旧#1 = 686 行）。引き下げ後 headroom と取り違えると 2〜4 倍の過大評価になる（`design.md` D-5 Amendment 2 の guardrail 表）。
  - **AC-6 の「+1 行追記で fail」の読み替え**: 余裕率が正である以上リテラルな 1 行では fail しないため、実効性の実証は `新値 − 実測 + 1` 行の追記で行う（`design.md` D-5 手順 5）。AC-6 の受入条件（上限が実効的であること）は変えない。

## ADR-12: 監査シートの数値正本を §1 の 1 表に集約する（同じ数値を複数節に書かない）

- **Context**: T-9 の implementation gate が 3 巡連続で `changes_requested` になり Fix Attempts 3/3 に到達した。実装物（`skills/gdd-brainstorming/SKILL.md`、blob `0a0b416e…`）は 3 gate 連続で clean で、指摘はすべて監査シート `docs/audits/r9-2-gdd-brainstorming-audit-20260729.md` の数値記載精度だった。巡 1（M-1 / M-2 / M-3）で grep 根拠・numstat・トークン値を訂正したが、巡 2（M-A / M-B / M-C）で「訂正が §1・§6 にしか適用されず同じ主張が §5・§7 に残存」して文書内矛盾となり、巡 3（M-D）では §4 節別判定の `## Goal` セルの bullet 数が実測と食い違った。同じ数値が複数節に散らばる構造が原因で、1 箇所直しても別の節に残る循環が起きていた。加えて remediation のたびに逐語復元でトークンと行数が動くため、シート作成時点の値は必ず陳腐化する。
- **Decision**: 監査シートの構造を変更し、**すべての実測値を §1「実測サマリ」表の 1 箇所にだけ書く**。各行に「再実測コマンド」列を併記する。他節は数値リテラルを書かず指標名で参照する。節別判定表は定性判定と対象名の列挙のみとし、bullet 数などの再導出可能な数値を持たない。適用は T-9 以降で、gate 通過済みの既存 4 シートは遡及移行しない。詳細手順は `design.md` § D-7。`Human Check Status=approved` / evidence `hc-20260731-6`（ユーザーが選択肢 3「構造を変える」を選択）。
- **Why**:
  1. **失敗モードを構造で塞ぐ**。数値の出現箇所が 1 つなら「他節への修正漏れ」（M-A / M-B / M-C 型）と「別節との自己矛盾」（M-D 型）は定義上発生しない。運用規律（「修正時に全走査する」）ではなく構造で担保する。
  2. **証跡性を落とさずに保守性を得る**。「固定値を書かず再実測コマンドだけを書く」案も検討したが、監査シートは AC-1 / AC-6 / AC-8 / AC-11 の判定証跡であり、値が無いと「その時点で何を確認したか」が残らない。固定値 + 再実測コマンドの併記なら、値が動いても §1 の 1 セルを更新するだけで済む。
  3. **AC を触らない**。変わるのは成果物の記法だけで、AC-1〜AC-11・Approved Direction・実装物のいずれにも影響しない。よって `design_detail_only`。
  4. **代替案はいずれも劣る**。(a) 記述セルを blocking から外す → 誤記が残ったまま通るだけで、証跡の信頼性が下がる（ユーザーも不採用）。(b) 監査シート検証スクリプトを新設 → design.md 決定 8「過剰設計の抑制」に反し、Wave 限定の作業成果物のために恒久ツールを増やす。(c) 既存 4 シートも遡って移行 → 承認済み証跡の改変にあたり、移行作業自体が新たな転記ミスを持ち込む。
- **Consequences**:
  - T-9 のシートを D-7 構造へ書き換え、M-D を訂正する（§4 の `## Goal` セルから数値を除去し、§1 に「`## Goal` bullet 数」指標行を追加して実測 21 → 14 を記録）。実測は `awk '/^## Goal/{f=1;next} /^## /{f=0} f' <path> | grep -c '^- '` で archive 21 / 蒸留後 14 を確認済み。
  - 適用後は機械確認 5 手順（行番号つき走査 → 逐語領域外の**測定値**判定 → §1 各行の再実測突合 → 逐語領域と §1 の一致確認 → remediation 直前の手順 3 再実行）を通してからコミットする。新規ツールは作らない。
  - **一元化だけでは「§1 の値そのものが古い・誤り」型（M-1 / M-2 / M-3）は塞げない**。一元化が防ぐのは「同じ誤りが複数節に散る」ことだけで、1 箇所の値が陳腐化することは防がない。唯一の防壁が手順 3 / 5 であり、そのために **再実測コマンドの終点を `HEAD` に固定しパス限定を必須**にする引数規約を設けた（終点に sha をリテラルで埋めると remediation 後も出力が変わらず素通りする = M-2 そのもの）。
  - 手順 2 は許容カテゴリの列挙ではなく**禁止側の正の定義**（「逐語領域の外に測定値を書かない」）で規定する。許容列挙は列挙漏れのたびに実行者がその場でカテゴリを追加することになり、D-5 が禁じる「ルールをその場で緩める」型と同型になるため。
  - 逐語コマンド出力は**コードフェンスまたは inline code span で囲む**書式規定を置く。地の文に裸で書くと手順 2 で違反判定され、かつ手順 4 の突合対象から漏れる。
  - §1 の実測値から四則演算で導ける値は §1 に指標行を立てず本文に計算式として書いてよいが、**式の入力は指標名で参照する**（リテラルとして現れるのは右辺のみ）。本文で 2 回以上使う導出値だけは §1 に指標行を立てる。
  - **外部由来値（目標値とその派生 / 他タスク・他 Wave の実測値）は §1 に指標行を立てず、出典を併記してリテラルで書く**。目標由来の値は「目標」列を起点に書き、目標が動いたとき §1 の 1 セル更新に追随させる。これがないと、対象成果物の測定値でない数値が手順 2 で分類不能になり手順が実行不能になる（目標値は既に 2 回動いている）。
  - **§1 は表を正本とし、表外に測定値を書かない**。正本は §1 の「表セル」であって §1 の範囲全体ではないため、手順 1 の awk は §1 の**表行だけ**を除外する（範囲全体を除外すると §1 内部の二重記載を検出できない。現行シートで実際に発生している）。
  - **inline code span を逐語領域として扱うのはコマンド出力の逐語引用に限る**。書式規定は出力側の義務であり「span 内なら逐語」という逆は成り立たない。明示しないと測定値を span に入れるだけで手順 2 を回避できてしまう。
  - **節見出しは `## <番号>. <名前>` に統一し §1 は `## 1. 実測サマリ`** とする。手順 1 の awk が `^## 1\.` / `^## 2\.` に依存するため、形式が崩れると fail-closed が誤発火する。
  - T-6 / T-7 / T-8 の監査シートは最初から D-7 構造で書く。`tasklist.md` の該当 Steps に D-7 参照と機械確認 5 手順の完了条件を追加する必要があるため、`gdd-task-breakdown` を再実行する。
  - **§4 / §5 は定性記述だが blocking のまま**。変わるのは「gate が数値突合すべき対象が §1 に一元化される」ことだけで、どの節も advisory には落とさない（§1 = AC 証跡、§6 flag / §7 検証結果も従来どおり blocking）。
  - 同一 Wave 内に 2 つのシート構造が並存する。シート本体は触らず、**PR 本文と completion 証跡に「T-2〜T-5 は D-7 適用前の構造」の 1 行**を入れて再指摘を防ぐ。
  - **限界**: 逐語領域は証跡そのものなので数値を含むことを許容せざるをえず、§1 との二重記載が 1 箇所だけ残る。書式規定（コードフェンス + inline code span）により手順 4 は機械判定可能だが、構造ではなく手順による担保である唯一の箇所という位置づけは変わらない。
