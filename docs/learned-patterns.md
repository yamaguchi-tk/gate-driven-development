# Learned Patterns

## Adopted Patterns

- **origin/main の高頻度更新下での版数衝突解決手順**: **（2026-09-12 廃止: PR は版数に触れず `changelog.d/` に断片を足す。正本は `plugins/gate-driven-development/docs/VERSIONING.md` § 版数はリリースでだけ上げる。以下は当時の記録）** 複数の並行 GDD セッションが同一 repo へ頻繁に PR をマージする環境では、`git merge origin/main` のたびに CHANGELOG.md の版数（`### [x.y.z]`）が他 PR と衝突しうる。解決手順は毎回同型: (1) `docs/VERSIONING.md` § 統合先が消費済みの版数を再利用しない に従い、自分の PR のエントリ見出しを「統合先の tip 版数 + 1」へ付け替える、(2) CHANGELOG.md 内で版数の降順（新しい方が上）になるようエントリ順を整える、(3) 3 manifest（`.claude-plugin` / `.cursor-plugin` / `.codex-plugin` の `plugin.json`）を同じ版数へ揃える、(4) `docs/VERSIONING.md` の「現行バージョン」と「統合先の消費済み版数」を更新する、(5) `gdd-codebase-health-baseline.json` の CHANGELOG 行数 ratchet（`current_lines` = 実測値+1）を再計算する。この手順は PR 旧#38（本パターンの出典）で 4 回連続で発生し、毎回同じ手順で機械的に解消できた（2026-09-06, `20260903-w29-pr-convergence-rules`）
- **codebase-health の `--mode changed` は merge コミット未確定の間は誤った結果を返す**: `gdd-codebase-health.py --mode changed` の内部実装は `git diff <base>...HEAD`（履歴ベース）に加えて `git diff` / `git diff --cached`（作業ツリー・staged の未コミット差分）も changed-file 集合に含める。`git merge` の conflict 解消中（まだ `git commit` していない状態）でこれを実行すると、merge で取り込んだ**全ファイル**が "changed" と誤認され、無関係な pre-existing の high finding が大量に紛れ込む。**対策**: merge commit を確定させてから computed-health を実行する。commit 前に確認したい場合は `--base-ref` に origin/main の tip を渡しても意味がない（staged diff が支配するため）ことを認識しておく（2026-09-06, `20260903-w29-pr-convergence-rules`）
- **state.md のサイズ上限超過時のトリム手順**: `run-steering-write-hook.sh` は `state.md` を 20000 byte 以内に制限する。長時間セッションで Round ごとの評価詳細を毎回 append すると容易に超過する。トリム優先順位: (1) 「Round N Implementation Review Status」「Round N Handoff Summary」等、番号付きの過去 Round 記録を丸ごと `worklog.md` へ移動し、現在値の field だけ残す、(2) `Approved Direction` / `Last Handoff Summary` 等の巨大な自由文 field を「短い要約 + `reviews.md` / `worklog.md` へのポインタ」に圧縮する、(3) 当時は AC Trace Ledger を AC ID ごとに最新 1 行だけ残し、過去の progression 行を `worklog.md` へ移した（今は Ledger を append-only の `ac-ledger.md` に置くので、Ledger の行は消さず、移さない。`references/ac-trace-ledger.md`）、(4) 既に `closed` / `pass-empty` 等で確定した Bounce Log・Refactor Gate Record・Notes の長大な過去記録も同様に圧縮する。この 4 段階で 124KB → 15KB まで削減できた（2026-09-06, `20260903-w29-pr-convergence-rules`）
- **時刻依存の受入条件は「測定基準に束縛した pass」で扱い、gate をループさせない**: **（2026-09-12 に `version-not-consumed` は統合先の版数との追従を要求しなくなった。正本は `plugins/gate-driven-development/docs/VERSIONING.md` § 版数はリリースでだけ上げる。「sha の組に束縛した pass」という書き方の教訓は、他の時刻依存の受入条件に引き続き当てはまる。以下は当時の記録）** `tests/validate-plugin.sh` の `version-not-consumed` は「自 branch が記録した統合先の消費済み版数」と「その時点の `origin/main` が ship している版数」を比較する。`origin/main` が高頻度に進む repo では、同期した直後から red へ戻るため、AC に「`validate-plugin.sh` が通る」とだけ書くと **completion gate が原理的に収束しない**（本タスクでは Round 2 以降 v0.40.10 → v0.40.11 → v0.40.12 → v0.40.13 と **4 回**追従し、うち 1 回は completion-reviewer が同じ観点を blocking high として再検出した）。対策は追従の高速化ではなく **AC の書き方**: (1) evidence に「measured at HEAD=`<sha>` against origin/main@`<sha>`」を併記し、`status=pass` を**無条件の主張ではなく sha の組に束縛された主張**として記録する、(2) その後の `origin/main` 進行による red は差分の欠陥ではなく**追従レース**と切り分ける（衝突面が 3 manifest / CHANGELOG / VERSIONING に限られ、実装ファイルと disjoint であることを `git merge-tree` または実 merge で確認する）、(3) 解消は PR 作成 commit（`origin/main` を取り込む同一 commit で `docs/VERSIONING.md` を同期）でのみ行う。同型の受入条件は「CI が green」「lock file が最新」など他にもありうる（2026-09-06, `20260906-merge-gate-session-jurisdiction`）
- **`setUpClass` で外部プロセス出力を無防備に parse すると、1 本の失敗がクラス全体を診断不能な ERROR に変える**: `tests/test_merge_gate_hook_block_reason_quality.py` は `setUpClass` で hook サブプロセス群を起動し `json.loads(sample.reason)` を直接呼んでいた。hook が 1 本でも block を返さない・timeout すると `sample.reason` が空文字列になり、`JSONDecodeError` で **クラス内の全 test が setUp ERROR** になる。どの sample が・なぜ失敗したかは一切残らないため、負荷起因の flake が「原因未特定」のまま複数ラウンド残った（本タスクでは completion-reviewer が mutation を当てて初めて機構を特定できた）。fixture 側の `subprocess.run(..., timeout=10)` が実測 hook コスト（steering 300 件で 9.7〜10.1 秒）と同値なことも併せて疑うべきだった。**教訓**: setUp / setUpClass で外部プロセスの stdout を parse する場合は、失敗 sample の識別子・`returncode`・`stderr` を添えて fail させる（2026-09-06, `20260906-merge-gate-session-jurisdiction`）
- **fail-closed gate の block を削除するときは「同値」ではなく「絶対期待値の判定表」で pin する**: 「降格後の判定が `active: false` marker と一致すること」を相対比較で書くと、両側が同時に壊れた場合に検知できない。本タスクでは 6 入力 × marker 3 状態の判定表で block の有無と reason code を**絶対値**として固定し、さらに「降格ケースの通過集合が marker 不在時の真部分集合であること」を下限として重ねた。実装を一時 mutation する検証（降格代入の削除 / 検査の復活 / 無条件降格の 3 種）で、いずれも赤くなることを確認してから GREEN と判定した（2026-09-06, `20260906-merge-gate-session-jurisdiction`）
- **A/B の差分を bucket に分類するときは、判定順に依存しない「消える差分」チェックを別に置く**: 1 コマンドで複数の field が同時に変わる形（例: 位置引数の引用符付き演算子は `pr_number` と `unresolvable` が同時に変わる）では、if/elif の判定順で内訳が入れ替わる。本タスクでは判定順を 1 つ変えるだけで、`(42, 0, 84, 0)` が `(78, 0, 48, 0)` になった。合計と `other=0` は一致するので気づきにくい。さらに、`unresolvable` を優先する順では、同時に値が消える差分が `new_unresolvable` に吸われて `other` に出てこない。対策として、「PR 番号・repo_flag が消える / `unresolvable` が True→False」だけを判定順と無関係に数える補助スクリプトを併置し、fail-open の方向の差分が 0 件であることを別に確かめた（2026-09-11, `20260911-merge-gate-quoted-operator`）
- **`version-not-consumed` の追従レースは、`git merge origin/main` せず帳簿ファイルの直接更新だけで解消できる**: **（2026-09-12 廃止: 追従レースそのものが無くなった。PR は版数に触れず `changelog.d/` に断片を足す。正本は `plugins/gate-driven-development/docs/VERSIONING.md` § 版数はリリースでだけ上げる。以下は当時の記録）** `tests/checks/version-not-consumed.sh` は `git show <ref>:<path>` で統合先（既定 `origin/main`）の manifest / CHANGELOG を**読むだけ**で判定する設計であり、branch 側が統合先の commit を実際に merge していることは要求しない。そのため origin/main が別 PR で大量の無関係な変更（例: hook 実装や skill/contract の広範な改修）を含めて版数を進めていた場合でも、`git merge origin/main` で全履歴を取り込む必要はない。`docs/VERSIONING.md` の「統合先の消費済み版数」を実測値に更新し、CHANGELOG.md 見出し・3 manifest・関連 docs/adr の版数行を「統合先の版数 + 1」へ直接書き換えるだけで `version-not-consumed: OK` になる。**判断の目安**: `git merge --no-commit --no-ff origin/main` を試算し（commit しない）、conflict が版数帳簿ファイル（CHANGELOG.md / 3 manifest / VERSIONING.md）だけなら帳簿更新のみで済ませて `git merge --abort` する。それ以外のファイルまで自動 merge で取り込まれる場合は、無関係な差分を PR に持ち込む前に、それらのファイルが自分の `.steering/` の運用や既存テストの前提に影響しないか確認してから判断する。**注意**: 帳簿更新のみを選ぶと、branch 側の CHANGELOG.md から統合先の新しい entry が丸ごと欠落したままになり、GitHub はこの content conflict を自動解決しないため PR は conflicting 表示になる。PR レビューで「両エントリを保持したうえで取り込め」という具体的な指摘が来た場合や、conflicting 状態を PR 上で解消する必要が生じた場合は、`git merge origin/main` で実際に取り込む。3 manifest・VERSIONING.md は帳簿更新前に両側が同値になっていると無競合で auto-merge され、`docs/VERSIONING.md` 自身が警告する「衝突として可視化されない事故」になるため、merge 後は必ず現在の値を確認して手動で正しい版数へ書き直す（CHANGELOG.md は通常、新規 entry 挿入位置だけが衝突し、diff3 3-way merge で origin/main 側の entry 本文が一字一句変わっていないことを確認してから解消する）。本タスクでは 1 回目は done_guard.py 等 25 ファイルが巻き込まれる試算から帳簿更新のみを選んだが、2 回目（origin/main がさらに進んだ後、PR レビューで両エントリ保持を明示指示された時点）では実際に `git merge origin/main` を行い、CHANGELOG は無競合（自 entry の先頭挿入のみ）、3 manifest・VERSIONING.md は前述の「事故」が実際に発生していたため手動訂正した（独立レビュー実測、2026-09-11, `20260911-merge-gate-quoted-operator`）
- **性能回帰テストの時計を「性質ごとに 1 本」に分けると、閾値を緩めずに並列・外部負荷下の flaky を止められる**: 壁時計 1 本の絶対閾値に「入力長に対して二次で効かないこと」と「hook の運用 timeout より十分速いこと」の 2 性質を同時に担わせると、外部由来の CPU 負荷で壁時計だけが膨らんだときに前者の閾値まで巻き添えで落ちる（実測: 負荷下で壁時計 2.5 倍に対し CPU 時間は 1.6 倍）。対策は閾値の緩和ではなく分割で、二次計算量の検出は CPU 秒の据え置き閾値に載せ、運用 timeout との距離は壁時計 backstop（hook timeout ÷ 2）に載せる。閾値の導出元は設定ファイル（`hooks/hooks.json`）1 箇所に寄せ、既定値へのフォールバックを置かず `LookupError` で fail-loud にする（既定値を置くと hook 名の typo や構造変更で backstop が黙って無意味化する）（2026-09-12, `20260911-x37-test-timing-flakiness`）
- **CPU 秒の計測式は「自プロセス + 子孫プロセス」の 2 項からなり、各項を個別の契約テストで固定しないと片方が dead になっても suite が緑のまま**: `time.process_time()`（自プロセス）と `resource.getrusage(RUSAGE_CHILDREN)`（子孫）のどちらか一方だけでは、in-process 計測または subprocess 計測のどちらかで値が常に 0 になり、その CPU assert が恒真化する。本タスクでは `process_time()` 項を削除する mutation を当てても全 suite が緑のままで、completion reviewer が指摘するまで検出できなかった。**対策**: 計測式の各項に対して「その項がなければ 0 になる」入力を使った下限 assert（`assertGreater(cpu, 下限)`）を 1 本ずつ置き、各 mutation が**対応する 1 本だけ**を red にすること（巻き添えゼロ）を実測で確認する。「suite のどこかで赤くなる」では項ごとの判別力を示せない（2026-09-12, `20260911-x37-test-timing-flakiness`）
- **production の deny 境界を mutation で赤くする検証は、`git checkout -- <path>` で戻さない**: `git checkout -- <path>` は **index から**作業ツリーへ復元するため、mutation 中に `git add -A` 相当が 1 回でも走ると変異版を復元して `git status` が clean に見える。加えて、挙動保存かつ高速な mutation（本タスクの 旧#5 = 二重走査、実測 0.0143 秒）は全体回帰でもどのテストも赤くならないため、「全体回帰が緑」は漏出の backstop にならない。**対策**: repo 外 scratch へ `cp -R` したコピーを変異させ、production ファイルには一切触れない。復元を伴う手順を取る場合は 1 本ごとに `git diff --quiet HEAD -- <dir>` と `git diff --quiet --cached HEAD -- <dir>` を evidence に残し、PR 作成直前に `git diff --name-only origin/main...HEAD` で当該ディレクトリが 0 件であることを確認する（2026-09-12, `20260911-x37-test-timing-flakiness`）
- **gate 契約の上限（Round 上限等）を超えた状態の免除は、blocker が 0 件でもエージェントが自己判断してはならない**: 本タスクは completion-check の `Completion Rounds` が上限 2 に対し 3 に達したが、最終ラウンドは blocker 0 件で収束していた。completion-check は「上限の目的（同じ blocker を何周もさせない）は達成済み」と判断して `done` へ進もうとしたが、completion reviewer がこれを **workflow-integrity の blocking finding**（HITL ゲートの自己免除）として差し戻した。契約上の方式転換 3 択（撤回 / 再設計 / スコープ縮小）は「まだ直すものがある」前提の選択肢なので blocker 0 件では空振りになる。**正しい形**: 形式的な 3 択を出すのではなく、逸脱の事実（超過した契約・超過に至った経緯・現在の blocker 件数）を 1 問にまとめて人間の明示的な yes を取り、承認を `state.md` の `Human Waiver` に記録して PR 本文にも開示する（2026-09-12, `20260911-x37-test-timing-flakiness`）
- **hook サブプロセスのテストは、原則は本番と同じ timeout で起動する。ただし argv では実行不能な大きさの入力は例外にできる**: **（2026-10-26〜27 の変更: 見出しの原則は、今の規定ではない。hook を起動するテストの打ち切りを本番の timeout に揃えることは求めない。並列の全量テストの負荷で、正しく返る hook の壁時計も本番の timeout に届いて落ちたため、2026-10-26〜27 に、一部の helper とテストの打ち切りを、止まったときの保険の `hang_guard_seconds`〔hooks.json の timeout の 6 倍〕にした。打ち切りなしや、本番と関係のない literal の秒数で起動するテストも残っている。どのテストが何秒で打ち切るかの正本はコード〔`plugins/gate-driven-development/tests/_timing_budget.py` の `hang_guard_seconds` とその呼び出し元、各 helper の既定〕で、ここには書き写さない。替えた経緯は `plugins/gate-driven-development/changelog.d/20261026-merge-gate-test-hang-guard.md` と `20261027-parallel-suite-load-flakes.md`〔次のリリースで `plugins/gate-driven-development/CHANGELOG.md` の版の節に集める〕。打ち切りを延ばしたテストは、打ち切りでは本番の timeout に収まるかを見なくなる。以下は当時の記録）** 「遅い runner で flaky になる」ことを理由に安易に timeout を延ばすと、本番では時間切れで素通りになる入力をテストが pass させてしまう。merge gate の hook は hooks.json の timeout が 10 秒なので、共有 helper の既定も 10 秒に揃えた。ただし候補を使い切る入力（約 4.2MB）のテスト 2 件だけは、正本の並列回帰で `subprocess.TimeoutExpired`（10 秒）が実測され（単独実行では 2.6〜3.1 秒で pass）、この入力サイズは ARG_MAX（1MB）を超えるため argv 経由では本番で再現しえない。この 2 件に限り `timeout=60` の引数を共有 helper に足して例外化した。他のすべての呼び出しは既定の 10 秒のまま。**教訓**: timeout 延長は「flaky だから」で一律に許さず、(a) その入力が本番の実行経路で到達可能か、(b) 到達不能なら例外を共有 helper の引数化で最小に切ることを条件にする（2026-09-11, `20260911-merge-gate-quoted-operator`）

## Rejected Alternatives

- **`git rebase origin/main` での conflict 解消**: Claude Code の auto mode classifier が履歴改変系操作として拒否した。同じ統合を成し遂げたい場合は `git merge origin/main --no-edit` を使う（ユーザー承認済みの代替）。rebase が使える環境でも、この repo のように main が高頻度で更新される場合は merge の方が「毎回コンフリクトを 1 コミットにまとめて解決できる」利点がある（2026-09-06, `20260903-w29-pr-convergence-rules`）

## Code Conventions Discovered

- `gdd-codebase-health-baseline.json` は `large_files`（行数 ratchet）のみをカバーし、`python_cyclomatic_complexity` / `python_function_count` の finding には baseline 免除の仕組みが無い。pre-existing な複雑度超過は「現状維持」の disposition を記録するだけでは `gh pr create` の Pre-PR Gate（Codebase Health Gate）で不足になる場合がある（同ファイルが PR の diff に含まれ、かつ複雑度が閾値超過のままだと機械的に high finding になる。当時は block され、今は pre-PR gate が `health-high` を実行後に通知する）。実際に小さな extract-function リファクタで解消する必要があった（`plugins/gate-driven-development/scripts/lint-hitl-stage-plan.py`）
- 版数を持つファイルは 4 箇所（`.claude-plugin/plugin.json` / `.cursor-plugin/plugin.json` / `.codex-plugin/plugin.json` / `docs/VERSIONING.md`）＋ CHANGELOG.md の見出しで、計 5 箇所すべてを同時に更新する必要がある。1 箇所でも古い値が残ると `tests/checks/version-not-consumed.sh`（層 A）が exit 1 になる
- `set -euo pipefail` 下のシェル hook では、**「直後に `exit 0` する呼び出し」と「処理を継続する呼び出し」で同じ関数の危険度が変わる**。ログ関数のように `HOME` 未設定（`set -u`）や外部コマンド不在（`pipefail`）でシェルごと即死しうる関数は、継続経路から呼ぶ場合だけ `( ... ) 2>/dev/null || true` の subshell + `|| true` で二重に封じる必要がある（`|| true` だけでは `set -u` の死を捕まえられない）。即死は「block を返せずに無出力で終わる」= silent fail-open になる。判定経路（block へ倒す側）は `if ( ... ) 2>/dev/null; then` の形にする（`|| true` を付けると block へ倒せなくなる）

- **バージョン bump を「5 箇所の同時更新」として検証する契約テストは、各箇所に独立の `assertGreaterEqual`（floor check）をかけるだけでは「同時更新されたこと」を直接検証できない**: `tests/test_verification_closed_grammar_release_notes_contract.py` の `VersionBumpContractTests` は当初 `assertEqual(TARGET_VERSION, ...)` で実装されており、これは次のバージョン bump で必ず赤くなる欠陥だった（`assertEqual` → `assertGreaterEqual` の semver tuple 比較へ緩和する一次修正を試みた）。しかしこの一次修正は各箇所を**独立に** floor check するため、3 manifest がそれぞれ異なる値（例: 0.42.0 / 0.42.1 / 0.42.2）でもテストは通ってしまい、「5 箇所を同時更新する」契約を直接検証できていなかった（人間レビュアーの指摘で判明。並行 PR 側も同種の脆弱パターン——`assertEqual` を別リテラルに置き換えただけ——で独立に「修正」しており、同じ conflict を再生産していた）。**正しい形**: 基準値（`.claude-plugin/plugin.json` の version）を 1 箇所から読み、残り 4 箇所（2 manifest + `docs/VERSIONING.md` + CHANGELOG 先頭見出し）が基準値と**完全一致**することを検証したうえで、基準値だけを別途 `TARGET_VERSION`（固定の歴史的フロア値）以上と floor check する canonical-source 設計にする。5 箇所への `assertGreaterEqual` を独立にかけるだけの設計は、一見無害に見えても「同時更新」の契約を検証できていない点に注意する（2026-09-11, `20260911-x37-changelog-validation-policy`）
- **契約テストのトークンに、自分が追加する CHANGELOG entry の本文で使う語句をそのまま使うと、トークン一致が無意味になる**: `tests/checks/hooks.sh` の `require_tokens()` はファイル全体への部分文字列一致であり、規約文の**所在**を見ない。CHANGELOG の Policy に新規約を追加する変更で、同じ PR 内に追加する CHANGELOG entry の説明文がその規約文を引用すると、規約行を削除してもトークンが entry 側に残って check が exit 0 のままになり、「規約が消えたら赤になる」という契約テストの目的が無効化される。**対策**: (1) 変異実測（規約文を削って赤になることの確認）は、entry 追加を含む**最終ツリー**で行う（実装途中の中間ツリーでの確認は stale evidence になる）、(2) トークンは**規範箇所（Policy）1 箇所にのみ**一致する部分文字列を選ぶ。Policy と Entry Template（記入例）の両方に出現する語句を選ぶだけでは不十分——規範側（Policy）の規約行だけを削除しても、Entry Template 側にトークンが残って check が exit 0 のままになる（人間レビュアーの指摘で判明。「Policy / Entry Template のいずれにも出現しない」を満たすだけでは、Policy 単独削除に対する片側検出力が保証されない）（2026-09-11, `20260911-x37-changelog-validation-policy`）
